# 로그인 만료 토큰 정리 분리 전후 성능 비교

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

로그인에서 전역 만료 DELETE를 제거하고 별도 스케줄러가 한 번에 최대 1,000개를 정리하도록 변경했다. 비밀번호 해시 비용, 사용자 잠금, 토큰 만료·재사용·폐기 검증은 유지했다.

## 측정 조건

- 동일 격리 DB에서 변경 전후 각각 50/100/500명, 조건별 3회: 본 비교 18회·3,900요청.
- 사용자 101,500명, 토큰 105,000개 중 만료 1,000개. 기존 인증 인덱스 3개와 주문 인덱스를 모두 유지했다.
- 앱·DB 각각 CPU 0.5개/768MiB, BCrypt cost 10, 클라이언트 제한 30초. 외부 결제·메일·AI 호출 없음.
- 매 회 앱 재시작, 단일 로그인 예열, 토큰 초기화 후 동시 요청. 시작 준비 동안만 CPU 2개를 사용하고 측정 전 0.5개로 복구했다.
- 변경 전 블록 다음 변경 후 블록으로 고정 순서 실행했다. 각 표 P95는 3회 P95의 중앙값이며 전체 요청을 합친 P95나 신뢰구간이 아니다.
- 이전 인덱스 보고서 수치를 재사용하지 않고 두 이미지를 새로 측정했다. 이번 배경 토큰의 미래 시각은 2030-01-01, 만료 시각은 2026-01-01이다.
- 기본 60초 조건의 수집 구간에는 양수 정리 기록이 없었고 만료 1,000개가 남았다. 실제 동시 정리는 별도 1초 설정으로 검증했다. 준비 과정부터 수집한 스케줄러 로그도 원본 JSON에 남겼다.

## 정량 해석

- 50명: 성공률 90.67% → 100.00%, HTTP403 14 → 0건, 시간 초과 0 → 0건. 전체 P95 감소율 23.30%.
- 100명: 성공률 96.67% → 100.00%, HTTP403 10 → 0건, 시간 초과 0 → 0건. 전체 P95 감소율 7.18%.
- 500명: 성공률 37.07% → 39.27%, HTTP403 6 → 0건, 시간 초과 938 → 911건. 전체 P95 감소율 -1.53%.

실패 포함 P95이므로 성공 수가 다른 조건의 지연 감소율을 정상 응답 속도 배수로 해석하지 않는다. 500명에서는 클라이언트 제한에 도달한 요청이 많아 P95가 약 30초에 머문다. 이번 변경은 만료 삭제 경합을 줄이는 실험이며 BCrypt의 CPU 비용과 로그인 중 DB 연결 점유 구조는 그대로다. BCrypt 자체 비중을 프로파일링하지 않았으므로 모든 잔여 지연을 특정 연산 하나의 탓으로 단정하지 않는다.

SQL은 performance_schema digest의 전후 카운터 차이다. 정확한 요청당 SQL 감사 기록이나 누락 없는 전체 실행 수로 단정하지 않는다. 데드락 문자열 수는 중복 로그를 포함해 고유 데드락/실패 요청 수와 다르다. HTTP403은 실제 수신 상태이며 자격 증명 오류로 단정하지 않는다. 새 코드의 전역 삭제 제거는 소스·회귀 검증과 함께 판단한다.

## 정리와 로그인 동시 실행

별도 3회·300요청은 주기를 1초로 줄였다. 초기 토큰을 모두 미래로 설정한 뒤 100명 로그인을 시작하고 약 2초 후 배경 1,000개를 만료로 바꿨다. 본 비교에 합산하지 않는다. 보수적인 시작/종료 여유 구간 안에서 양수 정리 로그가 남아 요청 처리와 겹쳤는지 확인했다.

## 기능·보안 검증

- 실제 MySQL에서 스케줄러가 만료 2,001개를 1,000/1,000/1개로 나눠 제거했다. 미래 시각 sentinel 1개, 배경 97,999개, 기존 사용자 세션 5,000개를 보존했다.
- 성공한 각 로그인 사용자의 새 토큰 저장, 64자리 해시 형식, 미래 만료 시각, 기존 미래 세션 보존을 DB에서 확인했다. 시간 초과 뒤 커밋한 요청이 있을 수 있어 새 저장 건수는 HTTP 성공 수보다 클 수 있다.
- 백엔드 전체 318개 중 315개 통과, 기존 3개 건너뜀, 실패/오류 0개. Dockerfile의 test bootJar도 통과했다.
- 정확한 만료 경계, 유효 토큰 보존, 최대 1,000개, 다음 배치, 독립 커밋, 만료 JWT와 DB 만료의 독립 거부, 실제 스케줄 실패 후 다음 주기 재시도는 자동 테스트로 검증했다.
- 독립 코드 검토에서 수정이 필요한 발견은 없었다. 실패 후 재시도 테스트는 DB 변경 전 오류를 주입했으며 부분 변경 후 장애를 별도로 주입하지 않았다.

## 범위와 남은 제한

- 운영 배포·장시간 지속 부하·다중 앱 인스턴스 동시 정리는 시험하지 않았다. 여러 인스턴스는 같은 대상을 볼 수 있어 일시적 잠금 경합이 남지만 삭제 시 만료 조건을 재검사한다.
- 정리는 기본 최초 60초 후 시작하고 작업 종료 후 60초 간격이며 한 번에 최대 1,000개다. 만료 발생량이 처리량보다 많으면 배치 크기·주기를 재조정해야 한다.
- 저장된 environment-before.json은 초기 상태 파일과 이름이 겹쳐 baseline 선택 후 상태를 담는다. 원래 서비스 메타데이터는 유지됐으며 실행기 내부의 진짜 최초 상태와도 finally에서 비교했다.
- 원래 free_ticket_db와 backend-redis-1의 ID·실행 상태·시작/종료 시각을 보존했고 측정용 3개 서비스만 종료했다. 운영 DB와 AWS에는 접근하지 않았다.
- JWT·쿠키·비밀번호·토큰 해시는 보고서에 저장하지 않았다. 원본 결과와 스크럽한 로그, 이미지 ID, 설정은 results/에 있다.
