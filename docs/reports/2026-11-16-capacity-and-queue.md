# 운영 구성에서의 처리 한계와 예매 대기열

측정일: 2026-11-16~17. [11/14 화면 단위 재측정](2026-11-14-page-api-remeasure.md)이 남긴 "연결 한도(8,192)가 남은 병목"을 운영과 같은 구성에서 다시 확인했다. 그 결과로 [예매 대기열](../design/waiting-queue.md)을 만들고 같은 환경에서 효과를 쟀다.

## 결론

- **11/14 결론은 운영에 그대로 맞지 않았다.** 11/14 시험은 부하 도구가 Tomcat에 직접 붙었고 CPU 제한도 없었다. 운영과 같은 2 vCPU, Caddy(HTTPS) 경유로 재면 **연결 한도보다 CPU가 먼저 막힌다.** Caddy의 HTTPS 처리가 CPU 1개 가까이를 쓴다.
- **연결 한도를 올리면 안 된다.** 과부하 때 Caddy는 밀린 요청마다 백엔드 연결을 새로 열어 결국 8,192에 닿았고, 그동안 Caddy 메모리가 2GB 넘게 늘어 컨테이너 합계가 최대 4.0GB였다. 운영 서버는 3.7GiB에 스왑이 없다. 한도를 올리면 더 많이 쌓일 뿐이라 바꾸지 않았다.
- **인기 티켓 하나에 몰린 주문은 초당 25건 근처가 한계다.** 병목은 CPU가 아니라 티켓 행 잠금이었다. 스레드는 여유가 있는데 DB 커넥션 10개가 모두 잠금을 기다렸다.
- **대기열로 주문 단계를 지켰다.** 3,000명이 30초에 걸쳐 몰릴 때, 대기열이 없으면 주문 p95가 10.9초, 있으면 **0.69초**이고 3,001명 모두 주문했다. 대신 마지막 사람은 약 2분을 기다린다(초당 20명 입장).
- **1만 명도 확인했다.** 1만 명이 100초에 걸쳐 오면 대기열로 10,001명 모두 주문했다(주문 p95 0.66초, 대기열이 없으면 성공률 35%). 20초 안에 몰리면 대기열이 있어도 19%만 성공했다.
- **대기열이 못 막는 구간도 확인했다.** 3,000명이 10초 안에 몰리면 공연 화면 조회와 대기열 등록만으로 서버 한계(일반 화면 초당 약 100명)를 넘는다. 이때도 주문 성공률은 99.7% 이상이었지만 주문 p95는 8~10초였다.
- **입구를 서버 밖으로 옮기자 20초 1만 명도 통과했다.** AWS에 운영과 같은 서버를 하나 더 띄우고 CloudFront·엣지 대기실(API Gateway·Lambda·DynamoDB)을 앞에 두니 **99.94%(9,995명)가 주문까지 마쳤다.** 같은 서버에 직접 붙으면 51%였다. 서버로는 입장한 사람의 주문(초당 약 20건)만 왔다. 처음에는 Lambda 동시 실행 계정 한도(10) 때문에 40%였고, 한도를 1000으로 올린 뒤 다시 쟀다. 이 구성은 11/18 운영에 적용했다.
- **측정 중에 대기열 버그를 하나 찾아 고쳤다.** 순번 확인이 "입장권 확인 → 순번 확인" 순서라, 그 사이에 입장 처리가 끼면 사용자가 어디에도 없는 것으로 보였다(0.8%). 순서를 바꾸고 재현 테스트를 추가했다.

## 환경

| | 운영 서버 | 측정 환경 |
|---|---|---|
| CPU | 2 vCPU (Lightsail 4GB) | 서버 쪽 컨테이너 전부를 CPU 2개(0,1번)에 고정. k6와 수집기는 다른 CPU |
| 메모리 | 3.7GiB, 스왑 없음 | 제한 없음, JVM 힙은 운영과 같게(`-XX:MaxRAM=3832m`, 최대 약 960MB) |
| 경로 | 브라우저 → Caddy(HTTPS, HTTP/2) → Spring Boot | 같은 Caddyfile, 같은 경로 |
| 구성 | 앱, MySQL 8.0, Redis, Caddy, Prometheus, Grafana | 같음 |

- 데이터: 11/14와 같다(공연 1,000개, 티켓 1,721개, 결제 주문 47,007건). 예매 측정용으로 재고 100만 장의 "인기 티켓"과 사용자 3,000명을 더했다.
- 예매 흐름의 로그인은 미리 서명한 토큰으로 대신했다. 로그인의 BCrypt 비용이 결과를 가리지 않게 하려는 것이다.
- 매 실행마다 앱과 Caddy를 새로 띄우고, Redis와 인기 티켓의 주문을 비운 뒤 예열하고 측정했다.
- 1초마다 앱 지표(Tomcat 연결·스레드, DB 커넥션, 힙)와 컨테이너 CPU·메모리를 기록했다.

## 2. 처리 한계 (Caddy 경유, 20초씩 2회)

처음 측정한 18회는 버렸다. 1단계 과부하 뒤 Caddy가 늘어난 메모리(1.1~2.6GB)를 놓지 않은 채로 측정이 이어져, 같은 조건의 결과가 100%와 20%로 갈렸다. 매 실행마다 Caddy를 다시 띄우고 다시 쟀다. 운영에서도 과부하 뒤 Caddy 메모리가 줄지 않을 수 있다는 점은 위험으로 남긴다.

## 3. 예매 오픈: 대기열 없음 vs 있음

3,000명이 한 공연의 인기 티켓에 몰린다. 대기열이 있으면 각 사용자는 대기열에 등록하고, 서버가 알려 준 간격(앞쪽 2초, 뒤쪽 최대 30초)으로 순번을 확인하다가, 입장권을 받으면 주문한다.

| 몰리는 속도 | 대기열 | 성공률 | 주문 단계 p95 (중앙값) | 공연 상세 p95 | 대기 시간 p95 | 순번 확인 요청 |
|---|---|---|---|---|---|---|
| 10초에 3,000명 | 없음 | 47% / 97% | 22.6~23.1초 (15~19초) | 21.9~23.1초 | - | - |
| 10초에 3,000명 | 있음 | 99.97% / 99.7% | 7.7~10.4초 (0.1~0.2초) | 13.5~14.5초 | 128초 | 초당 88~90건 |
| 30초에 3,000명 | 없음 | 100% | 10.9초 (6.6초) | 11.1초 | - | - |
| 30초에 3,000명 | 있음 (수정 후) | **100%** | **0.69초** (0.07초) | 0.97초 | 120초 | 초당 102건 |

- 대기열이 있으면 DB 커넥션을 기다리는 주문이 줄고, 주문 대부분이 0.1초 안팎에 끝났다.
- 순번 확인 요청은 초당 약 100건으로, 확인 간격을 순번에 맞춰 늘린 설계 덕분에 서버 한계(초당 약 440 요청)보다 충분히 작았다.
- 10초에 3,000명이 몰리면 공연 상세와 대기열 등록이 그 자체로 한계를 넘는다. 그 시간에 입장한 사람의 주문도 느려져 p95가 커졌다. 대기열은 주문 단계를 보호하지만, 들어오는 순간의 과부하는 막지 못한다.

### 1만 명

| 몰리는 속도 | 대기열 | 성공률 | 주문 단계 p95 (중앙값) | 공연 상세 p95 | 순번 확인 요청 | 마지막 사람 대기 |
|---|---|---|---|---|---|---|
| 100초에 1만 명 | 없음 | 35% | 23초 (13초) | 23초 | - | - |
| 100초에 1만 명 | 있음 | **100% (10,001명)** | **0.66초** (0.10초) | 0.81초 | 초당 187건 | 416초 |
| 20초에 1만 명 | 없음 | 2% | 23초 | 23초 | - | - |
| 20초에 1만 명 | 있음 | 19% | 20초 (0.12초) | 23초 | 초당 42건 | 221초 |

- 대기열 자체는 1만 명에서도 순서와 속도를 지켰고, 순번 확인 요청(초당 187건)도 서버가 감당했다.
- 20초에 1만 명(초당 500명)이면 공연 상세 조회 5,066건과 대기열 등록 2,844건이 시간 초과로 실패했다. 새 방문자마다 맺는 HTTPS 연결(Caddy)과 공연 상세의 DB 조회가 CPU 2개를 다 썼다. 서버 안의 대기열로는 입구 자체의 과부하를 막을 수 없다.
- 다음 단계는 입구를 서버 밖으로 옮기는 것이다. CDN에서 HTTPS를 끝내고 공개 데이터를 엣지에 캐시하며, 대기열 등록·순번 확인도 서버 밖(엣지 대기실)에서 처리해 서버에는 입장한 사람만 오게 한다.

## 4. CDN과 엣지 대기실 (AWS, 20초에 1만 명)

3절의 "20초에 1만 명"을 [CDN과 엣지 대기실](../design/edge-waiting-room.md)로 다시 쟀다.

- **서버:** 운영과 같은 사양의 측정용 Lightsail(2 vCPU, 4GB)에 운영과 같은 구성(Caddy, 앱, MySQL, Redis, Prometheus, Grafana)을 띄웠다. 운영 서버는 건드리지 않았다.
- **앞단:** CloudFront와 엣지 대기실 스택을 측정용으로 따로 만들었다.
- **부하:** k6를 이 PC에서 돌려 인터넷으로 보냈다. 3절(같은 PC 안)과는 환경이 달라 이 절 안에서만 비교한다.
- **시나리오:** 3절과 같다. 사용자 1만 명이 공연 상세 → 대기열 등록 → 순번 확인 → 인기 티켓 주문 → 결제 화면 순서로 간다. 대기 화면과 같게, 대기실이 과부하(429·5xx)면 1·2·4·8·10초 간격으로 최대 8번 다시 묻는다.
- **서버 지표:** 측정 구간의 최댓값을 측정 서버의 Prometheus에서 읽었다.

| 경로 | 성공률 | 공연 상세 p95 | 대기실 응답 p95 | 주문 p95 | 서버 CPU 최고 | 작업 스레드 최고 | DB 커넥션 대기 최고 | 서버가 받은 요청 |
|---|---|---|---|---|---|---|---|---|
| 서버에 직접 (서버 내 대기열) | 51% | 10.8초 | 11.2초 | 10.8초 | 100% | 200 | 190 | 최고 초당 341건 (대기열 242, 공연 상세 169) |
| 엣지, Lambda 한도 10 | 40% | 24ms | 68ms | 38ms | 32% | 2 | 0 | 대기열 0, 공연 상세 초당 0.5건 |
| 엣지, Lambda 한도 1000 | **99.94%** | 56ms | 72ms | 1.04초 | 53% | 40 | 30 | 최고 초당 43건 (주문 21.5건), 대기열 0, 공연 상세 0.4건 |

- **서버에 직접:** 3절과 같은 모습이다. 새 방문자의 HTTPS 연결, 공연 상세, 대기열 등록·순번 확인이 모두 서버 CPU를 써서 CPU가 100%에 닿았다.
- **엣지:** HTTPS는 CloudFront가 맺고, 공연 상세는 2초 캐시로 엣지가 대신 답하며, 대기열은 Lambda가 처리했다. 서버에는 입장한 사람의 주문과 결제 화면만 왔다.
- **Lambda 한도 10:** 새 AWS 계정의 Lambda 동시 실행 한도가 10이었다. 몰리는 순간 API Gateway가 503을 돌려줬고, 다시 묻기(12만 번)를 다 써도 자리를 못 받은 5,956명이 포기했다. 서버는 한가했다(CPU 32%). 필요한 동시 실행은 평소 약 25, 처음 몇 초(콜드 스타트) 약 200으로 계산해 한도를 1000으로 올렸다.
- **Lambda 한도 1000:** 다시 묻기는 32번으로 줄었다. 실패 6건은 모두 처음의 공연 상세 조회였고, 대기열과 주문에서 실패한 사람은 없었다. 대기 시간은 중앙값 약 4분, 최대 약 8분으로 초당 20명 입장 계산(500초)과 맞는다.
- **주문 p95 1.04초:** 한도 10일 때는 끝까지 간 사람이 적어 주문이 띄엄띄엄 왔지만, 이번에는 초당 20건이 8분 동안 같은 인기 티켓 하나에 이어졌다. DB 커넥션 대기가 최고 30이었다. 초당 20건은 이 티켓의 행 잠금 한계(초당 약 25건)에 가까워, 주문이 잠금을 기다리며 커넥션을 잡고 있던 것으로 본다.

## 5. 측정 중 발견한 대기열 버그

30초 3,000명 첫 측정에서 순번 확인 23건(0.8%)이 "대기열에 없음"(404)으로 실패했다.

- 원인: 순번 확인이 ① 입장권이 있는지 → ② 대기열 순번 순서로 읽었다. 입장 처리는 대기열에서 빼면서 입장권을 만드는 일을 한 번에 하지만, 두 읽기 사이에 입장 처리가 끼면 ①에서는 입장권이 아직 없고 ②에서는 이미 대기열에서 빠져 있다.
- 수정: ② 대기열 순번을 먼저 보고, 없으면 ① 입장권을 본다. 대기열에서 빠졌다면 입장권은 이미 있다.
- 검증: 입장 처리를 돌리는 동안 4개 스레드가 100명의 순번을 계속 확인하는 테스트를 추가했다. 수정 전 코드에서는 실패하고 수정 후에는 통과한다. 다시 측정하면 3,001명 모두 성공했다.

## 한계

- 부하 생성기와 서버가 같은 PC를 쓴다(CPU는 분리). 절대 시간보다 병목 위치(스레드·CPU vs 잠금·DB 커넥션)와 대기열 유무의 차이를 근거로 삼는다.
- 조건마다 2~4회다. 처리 한계 부근에서는 같은 조건에서도 결과 편차가 크다.
- 브라우저의 정적 파일과 이미지 요청은 포함하지 않았다.

- **엣지 대기실의 규모:** 공연마다 번호 카운터가 DynamoDB 항목 하나라, 한 공연에 초당 약 1,000명 넘게 등록하면 그 항목의 쓰기 한도에 닿는다. 그보다 커지면 카운터를 여러 개로 나눈다. Lambda 동시 실행 한도도 예상 최대 부하에 맞춰 미리 올려 둬야 한다.
- **주문 잠금 시간:** 주문마다 결제 대기 수량을 다시 합산하지 않도록 티켓에 점유 수량을 두는 방법. 만료·취소·결제 복구 경로를 모두 바꿔야 해서 별도로 진행한다.
- **과부하 뒤 Caddy 메모리:** 운영에서 Grafana로 관찰하고, 필요하면 Caddy 컨테이너에 메모리 상한을 둔다.
