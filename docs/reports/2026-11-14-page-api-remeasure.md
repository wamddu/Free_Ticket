# 화면 단위 성능 재측정: 9월 버전과 현재 버전 비교

측정일: 2026-11-14. [9/25 화면 단위 측정](2026-09-25-page-api-performance.md)에서 찾은 병목을 고친 뒤, 같은 시나리오로 개선 전후를 비교했다.

## 결론

- **DB 작업이 크게 줄었다.** 1초에 1,000명이 방문할 때 순위 집계 SQL은 757회에서 7회로, 공연 목록 SQL은 749회에서 0회로 줄었다. 20초 동안 1만 명이 방문할 때 주요 SELECT의 DB 시간은 40.5초에서 1.3초로 줄었다.
- **응답 시간도 줄었다.** 장르 화면 p95는 1초 500명에서 129→81ms, 1초 1,000명에서 1,570→1,043ms다. 20초 1만 명 시험의 API p95는 660→406ms다.
- **서버 연결 한도가 남은 병목이다.** 20초 1만 명 시험에서 기본 설정으로는 두 버전 모두 화면의 약 20%가 실패했다. 실패는 DB와 무관하게 모든 API에서 같은 시점에 난 20초 시간 초과였다. 연결 한도만 올리면 두 버전 모두 100% 성공했다.

## 비교 대상

| | 개선 전 | 개선 후 |
|---|---|---|
| 버전 | 9/25 측정에 사용한 JAR 그대로 (SHA-256 `1e4850d6…`) | main `25c3db3` |
| 주간 순위 | 방문마다 전체 판매량 집계 | 최근 7일 결제 기준, 60초 캐시 |
| 공연 목록 | 장르의 전체 공연을 한 번에 반환 | 30개씩 페이지 나누기, Redis 캐시 30초 |
| 장르 화면 API | 인증 갱신, 목록(전체), HOT, 주간 순위 | 인증 갱신, 마감 임박 5개, 최신 30개, HOT, 주간 순위 |

각 버전은 그 시점의 실제 프론트가 보내는 요청을 그대로 보냈다. 개선 후 장르 화면은 요청이 하나 더 많다.

## 환경과 방법

- 로컬 PC(Docker Desktop, 12 CPU) 한 대에서 앱, MySQL 8.0, Redis, k6를 각각 컨테이너로 실행했다. 자원 제한은 두지 않았다(9/25와 같음).
- 두 버전이 같은 DB를 쓴다. Flyway로 현재 스키마를 만든 뒤 데이터를 넣었다.
- 데이터: 공연 1,000개, 티켓 1,721개(9/25와 같은 생성 방식), 사용자 2,000명, 결제 완료 주문 47,007건. 주문의 수량 합계는 각 티켓의 판매 수량과 같고, 결제 시각은 최근 14일에 고르게 분포한다. 새 주간 순위가 실제로 집계할 데이터를 두기 위해 주문을 넣었다.
- 시나리오: 9/25와 같은 8개 화면(메인, 장르 6개, 상세)을 같은 비율로 섞었다. k6 `constant-arrival-rate`, 요청 제한 20초.
- 매 실행마다 앱 재시작 → Redis 비움 → 화면별 1회 예열 → 초당 200명 5초 예열 → 6초 대기 → `performance_schema` 초기화 → 측정 순서로 진행했다.
- 1초 급증은 개선 전·후·후·전·전·후, 20초 시험은 전·후·후·전 순서로 번갈아 실행했다. 표의 값은 반복 실행의 중앙값이다.

## 결과: 1초 급증

| 부하 | 버전 | 성공 / 시작 | 메인 p95 | 장르 p95 | 상세 p95 | 순위 집계 SQL | 공연 목록 SQL |
|---|---|---:|---:|---:|---:|---:|---:|
| 500명/1초 | 개선 전 | 1,503 / 1,503 | 97ms | 129ms | 141ms | 383회 | 375회 |
| 500명/1초 | 개선 후 | 1,542 / 1,542 | 104ms | **81ms** | 129ms | **7회** | **0회** |
| 1,000명/1초 | 개선 전 | 2,994 / 2,994 | 1,420ms | 1,570ms | 1,710ms | 757회 | 749회 |
| 1,000명/1초 | 개선 후 | 3,046 / 3,046 | 1,030ms | **1,043ms** | 1,044ms | **7회** | **0회** |

성공·시작 수는 3회 합계다. SQL 횟수는 측정 구간의 `performance_schema` 기록이다. 개선 후의 순위 집계 7회는 예열 뒤 5초 HOT 캐시가 만료되어 키(메인과 장르 6개)마다 한 번씩 다시 계산한 것이다. 주간 순위는 60초 캐시, 공연 목록은 예열 때 채운 Redis 캐시에서 응답했다.

1초 1,000명 조건의 화면 시간에는 연결 수립 시간이 크게 들어 있다. 2,000개의 가상 사용자가 동시에 연결을 맺느라 두 버전 모두 연결 단계 p95가 약 1초였다. 서버가 응답한 시간(k6 `http_req_duration` p95)만 보면 실행별로 개선 전 287~1,837ms, 개선 후 93~526ms였다. 실행마다 편차가 커서 응답 시간보다 DB 작업량을 더 확실한 근거로 본다.

## 결과: 20초 동안 1만 명

### 기본 설정에서는 두 버전 모두 약 20% 실패

| 버전 | 성공 / 시작 (2회 합계) | 실패 유형 |
|---|---:|---|
| 개선 전 | 16,695 / 20,002 | 모두 요청 시간 초과(20초) |
| 개선 후 | 15,915 / 20,036 | 모두 요청 시간 초과(20초) |

실패한 요청은 측정 시작 직후에 보낸 것들이었다. DB를 쓰지 않는 인증 갱신 API도 다른 API와 같은 비율로 실패했다. 가상 사용자 4,000개가 `http.batch`로 여러 연결을 동시에 열고 유지하므로, 서버의 연결 자리(Tomcat `max-connections` 기본 8,192)가 차서 새 요청이 처리되지 못한 것으로 판단했다. 9/24~25 HOT 진단에서 확인한 것과 같은 현상이다. 개선 후 버전은 장르 화면 요청이 하나 많아 연결도 더 많이 쓴다.

### 연결 한도만 올린 확인 시험

원인을 확인하려고 `SERVER_TOMCAT_MAX_CONNECTIONS=30000`만 바꿔 버전별로 한 번씩 다시 실행했다.

| 버전 | 성공 / 시작 | 장르 p95 | 상세 p95 | API p95 | 순위 집계 SQL | 주요 SELECT DB 시간 |
|---|---:|---:|---:|---:|---:|---:|
| 개선 전 | 10,000 / 10,000 | 1,030~1,114ms | 1,390ms | 660ms | 7,527회 (21.4초) | 40.5초 |
| 개선 후 | 10,001 / 10,001 | 1,085~1,151ms | 919ms | **406ms** | **28회 (0.08초)** | **1.3초** |

두 버전 모두 실패가 사라졌으므로, 기본 설정의 실패는 연결 한도 때문이었다. 이 조건에서 장르 화면 p95는 비슷했다. 개선 후 버전이 화면당 요청을 하나 더 보내는 데다, 이 부하에서는 연결 관리 비용이 화면 시간을 좌우한다. DB 시간은 약 31분의 1로 줄었다. 주요 SELECT는 실행 시간 상위 12개 SQL 기준이다.

## 한계

- 부하 생성기와 서버가 같은 PC를 쓴다. 절대 응답 시간은 운영 환경의 수치가 아니다.
- 1초 급증은 버전별 3회, 20초 시험은 2회, 연결 한도 확인은 1회씩이다.
- 운영 서버의 연결 한도는 아직 바꾸지 않았다. 바꾸려면 메모리와 스레드 사용량을 함께 확인해야 한다.
- 브라우저 렌더링, 정적 파일, 이미지 로딩은 포함하지 않았다.
