# 로그인 병목 진단 — 2026-11-01

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

결론: 이번 극한 로컬 실험의 주 병목은 **앱 CPU 0.5개 제한 아래의 BCrypt 비밀번호 검증**이다. 로그인 트랜잭션이 비밀번호 검증 중에도 DB 연결과 사용자 행 잠금을 유지하는 구조가 연결 대기를 추가한다. 만료 토큰 정리를 분리한 뒤에도 남은 지연은 이 처리 용량과 대기 구조로 설명된다.

동일한 앱 이미지와 DB에서 앱 CPU만 0.5→2로 바꾼 결과, 100명 P95가 약 3.50배 개선됐다. 연결 풀만 늘리면 대기 위치는 바뀌지만 전체 개선은 작았다. 따라서 추가 인덱스나 풀 확장만으로 현재 지연을 해결하기는 어렵다.

**실험 조건과 비교 결과**

- 매 실행 앱 재시작, 풀 사전 확보, 실제 로그인 1회 준비 후 토큰 데이터 원복. 준비 시 CPU 2개는 측정에서 제외하고 목표 CPU로 복원 후 측정했다.

**비밀번호 계산 자체가 얼마나 무거운가**

성공한 100명 별도 계측에서 BCrypt CPU 평균은 **53.59ms/요청**, 컨트롤러 요청 스레드 CPU 평균은 **61.21ms/요청**이었다. BCrypt가 이 범위의 실제 스레드 CPU 시간 중 **87.54%**를 차지했다. 전체 컨테이너 CPU의 비율은 아니다.

같은 이미지의 실제 Spring Security 구현·동일한 cost10으로 DB·네트워크·HTTP를 모두 제외하고 검증만 따로 실행했다. 고정 10개 작업 스레드, 사전 검증 20회, 측정 100회씩이며 둘 다 100/100 일치했다.

| CPU | 검증당 CPU 시간(ms) | 검증만 실제 처리량(회/초) | CPU 원가로 계산한 단순 상한(회/초) |
|---:|---:|---:|---:|
| 0.5 | 53.305 | 9.238 | 9.380 |
| 2 | 59.117 | 33.267 | 33.831 |

상한식은 `CPU 할당량 / 검증당 CPU 초`다. 0.5 CPU에서 약 53ms의 검증만 해도 초당 약 9.38회를 넘기기 어렵다. 실제 로그인에는 JWT·ORM·HTTP·JVM 등 추가 작업과 대기가 있어 관측된 약 6.56건/초가 더 낮다. 순수 검증은 조건당 1회이므로 정밀 용량 예측이 아니라 CPU 원가를 확인하는 보조 실험이다.

비밀번호 검증 경과 시간은 평균 약 820ms인데 실제 CPU 시간은 약 54ms였다. 이는 요청이 검증에 진입한 뒤에도 계속 CPU를 받지 못하고 다른 작업과 순서를 나눠 쓴다는 증거다. CPU 비용과 응답까지의 경과 시간을 구분해야 한다.

**왜 DB 연결 대기도 길어지는가**

현재 실행 순서는 `트랜잭션 시작 → 사용자 FOR UPDATE 조회/연결 확보 → BCrypt 검증 → JWT/리프레시 토큰 저장 → 담당자 조회 → 커밋/연결 반환`이다.

표 구간은 겹친다. 연결 점유는 검증·JDBC·커밋을 포함하며 서비스 타이머는 바깥 트랜잭션 획득·커밋을 포함하지 않는다. 이 수치들을 합산해 응답 시간의 구성비로 만들면 안 된다. JDBC 경과 시간에는 드라이버·프로토콜·CPU 스케줄링 대기도 포함된다.

클라이언트 시간에서 컨트롤러 시간을 뺀 나머지도 크다(풀10 평균 약 4.26초, 풀40 약 6.13초). 여기에는 클라이언트/접속/네트워크/필터/요청 배정/응답 처리 등이 함께 들어 있다. 전부 Tomcat 대기열이라고 단정하지 않았다. 호스트와 컨테이너 시계가 약 10ms 어긋나 있어 ID로 연결하고 준비 요청 종료와 2초 이상 분리된 1초 범위로 시간 경계를 보정했다.

**SQL·행 잠금·GC는 무엇을 보여줬나**

대표 본 실험(0.5 CPU/풀10/100명/1회차)의 MySQL statement digest는 다음과 같다. 서버 실행 시간은 요청당이 아니라 표의 호출 전체 합계다.

| SQL | 기록된 호출 수 | 검사 행 수 합계 | 서버 실행 시간 합계(ms) |
|---|---:|---:|---:|
| 이메일 사용자 조회 FOR UPDATE | 100 | 100 | 27.544 |
| 리프레시 토큰 PK SELECT | 99 | 0 | 24.706 |
| 담당자 여부 조회 | 100 | 100 | 25.093 |
| 리프레시 토큰 INSERT | 100 | 0 | 25.004 |

기록한 SQL 실행 시간 소계는 **102.346ms/100요청**이며 COMMIT은 포함하지 않는다. 일부 digest 호출은 99회로 집계되어 정확한 요청 감사 기록으로 쓰지 않았다. 이 소계가 전체 DB 비용인 것은 아니다. 별도 계측 커밋 경과는 평균 42.67ms/요청이며, 이를 SQL 소계와 같은 경계로 해석하지 않는다.

실행 계획에서 사용자 이메일 조회는 유일 인덱스 `UK6dotkott2kjsp8vw4d0m25fb7` / `const` / 예상 1행, 담당자 조회는 기존 user_id 인덱스 `FKphv132ir3mgfmlst3xt6skafk` / `ref` / 예상 1행을 사용했다. EXPLAIN은 동일 조건의 단순화한 조회를 사용했으며 실제 FOR UPDATE 전체 SQL의 계획을 그대로 재현한 것은 아니다. 실제 호출·검사 행 수는 위 digest로 별도 확인했다. 담당자 테이블에 user_id 선두 인덱스가 없다고 주장할 근거는 없다. 리프레시 토큰은 문자열 ID 저장 경로에서 PK SELECT 후 INSERT가 관측됐지만 현재 주요 CPU 병목에 비하면 우선순위가 낮다.

프로파일 세 조건에서 1초마다 확인한 MySQL 행 잠금 대기는 모두 0이었다(각각 14/30/14개 표본). 짧은 잠금을 놓칠 수 있고, 서로 다른 사용자 실험이므로 같은 계정으로 반복 로그인할 때의 행 잠금 경합은 별도 문제다. FOR UPDATE 구조를 무조건 제거해도 안전하다는 뜻은 아니다.

JFR은 클라이언트 측정 구간 안의 이벤트만 선택했다. 다음 비율은 HTTP 작업 스레드의 Java 실행 표본 중 BCrypt 스택이 관측된 비율이다.

| 동시 사용자 / 풀 | BCrypt Java 실행 표본 | 최상위 GC 정지 횟수 | GC 정지 합계(ms) |
|---|---:|---:|---:|
| 100 / 10 | 99/114 (86.84%) | 0 | 0.000 |
| 500 / 10 | 164/210 (78.10%) | 2 | 230.055 |
| 100 / 40 | 31/42 (73.81%) | 0 | 0.000 |

이 비율은 정확한 프로세스 CPU 점유율이 아니다. NativeMethodSample의 accept/poll/epoll은 별도로 분석하고 CPU 표본에 합치지 않았다. GC 관련 이벤트는 서로 겹치므로 중복 합산하지 않았다. 수십 초 지연을 GC가 주도한다는 증거는 없었다.

앱 CPU 제한에 따른 throttling이 대부분의 할당 주기에서 관측됐고 앱 OOM/메모리 실패 증가는 없었다. 100명 0.5 CPU/풀10의 수집 구간 기준 CPU 할당량 활용 추정은 약 96.9%, DB는 약 9.4%였다. CPU를 늘린 비교에서도 DB는 같은 제한을 유지했다. 이것이 CPU 인과 실험을 뒷받침한다. DB 메모리 최대치는 과거 페이지 캐시를 포함해 제한에 도달한 적이 있으므로 DB 메모리가 충분하다고 단정하지 않는다.

수집 한계: 500명/0.5 CPU에서는 수집 명령 자체가 지연돼 시작 시각으로 계산한 CPU 활용 추정이 100%를 넘는 경우가 있다. 이는 CPU가 할당량을 지속해서 초과했다는 뜻이 아니다. 상세 집계에는 카운터 읽기 가능 구간의 보수적 범위를 별도로 남겼다. cgroup v1 throttled_time은 CPU별로 누적될 수 있어 벽시계 시간으로 나눈 비율을 만들지 않았다.

**다음 개선의 방향**

1. 운영 환경의 실제 CPU 할당량에서 동일한 실험으로 목표 로그인 처리량을 먼저 확인한다. 테스트용 0.5 CPU 제한은 일반 로컬/배포 Compose에 없는 별도 실험 설정이다. AWS 서버가 똑같이 제한되어 있다는 뜻이 아니다.
2. 연결을 보호하려면 비밀번호 검증을 짧은 DB 쓰기 트랜잭션 밖으로 분리하는 설계를 검토한다. 토큰을 발급할 때 사용자의 상태와 비밀번호 변경 여부를 잠금 안에서 재확인해 기존 동시성·보안 규칙을 보존해야 한다. 검증을 밖으로 옮겨도 BCrypt의 CPU 비용 자체가 사라지지는 않는다.
3. 목표 동시 로그인량이 CPU 계산 용량을 넘으면 그만큼 CPU/인스턴스를 확보하고 과도한 동시 요청을 제어한다. 연결 풀이나 요청 스레드만 늘리면 대기 위치가 이동할 수 있다. BCrypt 강도를 낮추거나 비밀번호 검증을 캐시하는 방식으로 해결하지 않는다.

만료 토큰 정리 분리는 요청마다 반복하던 DELETE와 충돌을 제거하는 개선이었다. 이번 실험은 그 작업과 만료 적체가 없어도 남는 CPU 한계를 확인했다. 정리 분리의 안정성 개선과 전체 로그인 처리 용량 개선은 구분해야 한다.
