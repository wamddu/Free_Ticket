# 이벤트 첫 페이지와 기존 전체 목록 비교

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

최종 36개 wave, 측정 요청 7,800개 중 7,800개가 SHA-256 검증을 통과한 HTTP 200이었다. 기존 warm 응답은 이벤트 3,500개 전체이며 새 응답은 첫 30개다. 두 조건은 반환하는 작업량이 다르므로 전체 데이터 처리 속도 향상으로 해석하지 않는다.

## 조건과 측정 방법

- 기존 이미지 `free-ticket-perf:redis-20261101-v2`의 전체 목록 warm 9개 wave와 새 이미지 `free-ticket-perf:pagination-20261101`의 first-page off/cold/warm 각 9개 wave를 같은 fixture에서 측정했다. 정확한 이미지 ID는 `results/method.json`에 있다.
- 동시 요청은 50/100/500개, 조건별 3회다. 앱·MySQL 각각 0.5 CPU·768MiB, Redis 0.5 CPU·192MiB 및 maxmemory 128MiB를 사용했다.
- 고정된 조건 블록 순서로 실행했다. 매 wave 앱 재시작 → 해당 기본 목록 단일 요청 예열 → 두 캐시 키 삭제. warm만 한 번 더 채웠다. cold도 JVM·DB는 예열되어 있다.
- 이전 runner와 같이 시작 준비 동안만 앱 CPU를 2로 올렸다가 0.5로 복구한다. 각 측정 직전 CPU·메모리 제한과 Redis maxmemory를 확인했다. 이미지를 실행 중에 빌드하지 않는다.
- 본문 수신 뒤 SHA 확인을 포함하는 `ms`는 이전 runner의 시간 정의를 유지했다. `read_ms`는 전체 본문을 수신한 즉시 기록해 SHA 확인을 제외했다. 본문을 받지 못한 실패의 read_p95 계산에는 종료까지의 경과 시간을 사용했다. 두 값 모두 클라이언트 이벤트 루프와 호스트 스케줄링 영향을 포함한다.
- 30초 클라이언트 제한, 실패 포함 전체 P95다. 표는 wave P95 3개의 중앙값 [최소~최대]이며 요청을 합친 P95나 신뢰 구간이 아니다.
- 앱·DB·Redis의 같은 모니터 수집을 모든 비교 조건에 사용했다. Docker stats 호출 완료 뒤 2초를 기다려 다음 표본을 수집한다. 정확히 2초 간격인 표본이나 자원 적분·비용 측정은 아니며 짧은 peak를 놓칠 수 있다.

## 정량 비교 해석

응답 본문은 전체 1,152,258바이트에서 첫 페이지 5,004바이트로 1,147,254바이트(99.57%) 줄었다. 이는 전체 3,500개 대신 첫 30개만 반환한 결과다.

| 동시 요청 | full-warm P95 중앙값, 초 | page-off P95 중앙값, 초 | page-warm P95 중앙값, 초 | full-warm → 첫 page-warm 감소율 | page-off → page-warm 감소율 |
|---:|---:|---:|---:|---:|---:|
| 50 | 1.055 | 1.044 | 0.301 | 71.48% | 71.20% |
| 100 | 2.216 | 1.841 | 0.585 | 73.59% | 68.22% |
| 500 | 9.936 | 7.218 | 3.205 | 67.74% | 55.60% |

감소율은 (비교 전 P95 중앙값 − 비교 후 P95 중앙값) / 비교 전 P95 중앙값 × 100이다. full-warm → page-warm은 3,500개 전체 응답과 첫 30개 응답의 지연 차이이며 동일 작업량의 속도 향상이 아니다. page-off → page-warm은 같은 첫 페이지를 반환하는 새 이미지의 캐시 비활성·사전 적재 차이다. 실패를 포함한 P95이므로 성공률 표와 함께 해석한다. 전체 페이지 누적 조회나 전체 데이터 내보내기의 개선율은 계산하지 않았다.

DB 카운터는 `performance_schema`의 SELECT·events·description 일치 digest `COUNT_STAR` 차이다. 정확한 요청당 SQL 수로 단정하지 않는다. Redis INFO keyspace 카운터는 서버 전체의 키 단위 조회 통계다. HGET에서 hash 키는 존재하지만 해당 field가 없는 경우도 keyspace hit로 집계될 수 있으므로 field 적중 수나 API 캐시 적중률이 아니다. double-check·TTL·관측 명령 영향도 포함한다. 경고는 로그의 캐시 경고 접두사 출현 수다. 리소스 표본별 원본은 wave JSON, 조건별 최대 표본은 `summary.json`에 보관했다.

## 응답과 기능 검증

- full: 서로 다른 이벤트 ID 3,500개, 1,152,258바이트, wire SHA-256 `02437471778282b4b56bbc8907b71e7e7691f79d3f5176e0ab75e157f1bdb888`. 해당 조건의 모든 성공 응답을 이 바이트 해시와 대조했다.
- page: 서로 다른 이벤트 ID 30개, 5,004바이트, wire SHA-256 `839737ecd126ee26b7e7ddfbd51c2efbdfa53b39e46b88e893d3c7971cfda6c7`. 해당 조건의 모든 성공 응답을 이 바이트 해시와 대조했다.
- 새 기본 응답은 page=0,size=30,hasNext=true이며 기존 latest 전체 목록의 처음 30개 ID와 일치했다. page=1은 다음 30개이며 겹침이 없다.
- 카테고리만 지정한 페이지, sort와 size가 다른 페이지가 서로 다른 hash field에 적재된다. closingSoon,size=5는 전체 3,500개를 endDate ASC,id DESC로 정렬한 전역 상위 5개와 일치했다.
- page=116은 20개·hasNext=false, page=117은 빈 목록·hasNext=false다. title/region/dateFrom/dateTo/maxPrice/availableOnly 필터는 캐시 field를 늘리지 않고 DB digest가 증가했다.
- 첫 hash TTL 29,436ms, page=1 추가 뒤 28,118ms로 감소했다. 추가 페이지 적재가 TTL을 연장하지 않았고 만료 뒤 키 제거와 DB 재적재를 확인했다.
- 격리된 테스트 DB의 관리자 이벤트 수정 커밋이 전체 page hash를 무효화했고 수정 내용을 확인했다. 원래 이름으로 복구했다. Redis 중단 중 동일 응답 HTTP 200을 확인했으며 단일 fallback 3015.72ms, Redis 재시작 뒤 캐시가 복구됐다.

## 범위와 한계

- first-page 응답 지연과 전송량을 비교했다. 전체 목록 조회와 같은 일을 더 빨리 수행한다는 주장은 하지 않는다.
- 이 실행은 격리된 `free-ticket-perf` 프로젝트만 제어한다. `free_ticket_db`에는 접근하지 않으며 기존 로컬 `backend-redis-1`의 컨테이너 ID·실행 상태·시작 시각이 유지되었는지 대조했다. 모든 perf 컨테이너는 finally에서 중단했다.
- before/after 환경 기록은 비밀값을 저장하지 않는 허용 목록을 사용했다. fixture는 기존 synthetic 3,000개와 기존 helper로 재생성한 Wave 500개다. 원본 데이터베이스의 snapshot을 수집하지 않았다.
- 고정 순서·각 세 번의 반복이며 장시간 부하, 다중 JVM의 동시 cache miss, 동시 이벤트 삽입 중 offset 이동, 모든 운영 장애는 검증하지 않았다. 페이지를 넘기는 동안 데이터가 바뀌면 offset 방식의 중복·누락 가능성이 남는다.
- 단위·회귀 테스트와 프론트엔드 검증은 별도의 최종 작업 기록을 확인한다. 이 생성기는 벤치마크와 단일 Docker 통합 시나리오만 검증한다.

## 구현 검증과 사용법

백엔드 전체 테스트는 308개 중 305개 통과, 기존 3개 건너뜀, 실패·오류 0개였다. 프론트엔드 16개 파일 124개 테스트, 프로덕션 빌드, 변경한 7개 파일의 ESLint가 통과했다. 백엔드 Dockerfile의 test·bootJar 빌드도 통과했다. 운영 배포는 이 측정 단계에서 수행하지 않았다.
