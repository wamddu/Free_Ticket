# Redis 이벤트 전체 목록 캐시 성능 비교

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

동일 이미지 `free-ticket-perf:redis-20261101-v2`의 캐시 비활성(off), 빈 키(cold), 사전 적재(warm)를 비교했다. 27개 wave에서 측정 요청 5,850개 중 5,234개가 HTTP 200이었다. 예열·준비·통합 점검 요청은 이 수에 포함하지 않는다.

## 측정 조건

- 대상은 필터 없는 `GET /api/events` 한 경로이며 이벤트 3,500개 전체를 반환한다.
- 동시 요청 50/100/500명, 각 조건 3회 반복. 앱과 MySQL은 각각 CPU 0.5개·메모리 768MiB로 제한했다.
- Redis는 별도로 CPU 0.5개·메모리 192MiB, maxmemory 128MiB를 할당했다. 캐시 조건에는 이 추가 서비스 자원이 들어간다.
- 같은 앱 이미지에서 활성화 환경 변수만 바꿨다. off는 기존 MVC 객체 직렬화 경로를, cold/warm은 완성된 JSON 바이트 재사용 경로를 사용한다. 따라서 DB 조회 생략과 JSON 재생성 생략을 함께 비교하며 과거 이미지와 비교한 값은 아니다.
- 실제 측정 블록 순서는 warm → off → cold이다. 각 블록에서 회차 1~3, 회차 안에서 50→100→500명 순서다. 순서를 무작위로 섞지 않았다. 표의 표시 순서와 측정 순서는 다르다.
- 매 wave 앱 재시작 → 전체 목록 단일 요청 예열 → Redis 키 삭제. warm만 추가 전체 요청으로 키를 채운 다음 측정했다. cold도 JVM·DB는 예열된 상태다.
- 같은 JVM에서 동시에 진행하는 Redis GET을 최대 32개로 제한해 큰 응답의 Redis reply buffer 누적을 제한한다. 초기 보정 측정은 `initial-calibration/`에 따로 보관하며 아래 최종 27개 wave에 섞지 않았다.
- TTL은 30초다. cold/warm은 시작 시 키 상태를 가리키며 wave 도중 만료·재적재가 가능하다. Redis hit/miss 기록을 별도로 제시한다.
- 클라이언트 제한은 30초다. 전체 P95는 실패·시간 초과를 포함한 클라이언트 경과 시간이며 실제 관측값은 제한 설정을 조금 넘을 수 있다.
- 격리된 Docker 테스트 환경을 사용했다. AWS·원래 로컬 DB는 접근하지 않았고 외부 결제·SMTP·Gemini 호출은 없다.

P95 중앙값과 범위는 각 wave P95 3개의 요약이다. 3개 wave를 합친 요청 분포의 P95나 신뢰 구간이 아니다. 성공 P95는 HTTP 200만 대상으로 같은 방식으로 요약했다.

## 기록된 DB digest 및 Redis 카운터

DB 값은 `performance_schema.events_statements_summary_by_digest`에서 SELECT 및 events·description 문자열과 일치하는 항목들의 `COUNT_STAR` 합계 전후 차이다. 요청당 정확한 SQL 횟수나 DB 전체 쿼리 수가 아니다. 예를 들어 off 50명 1회차는 요청 50개에 기록된 차이가 49였다. 이 수치만으로 정확히 N개 쿼리가 사라졌다고 주장하지 않는다.

| 동시 요청 | 조건 | DB digest 차이 중앙값 [최소~최대] | DB 차이 합계 | Redis hit/miss 합계 | Redis eviction 합계 | 캐시 경고 합계 |
|---:|---|---:|---:|---:|---:|---:|
| 50 | off | 48 [47~49] | 144 | 0/0 | 0 | 0 |
| 50 | cold | 1 [1~1] | 3 | 147/153 | 0 | 0 |
| 50 | warm | 0 [0~0] | 0 | 150/0 | 0 | 0 |
| 100 | off | 97 [96~98] | 291 | 0/0 | 0 | 0 |
| 100 | cold | 1 [1~1] | 3 | 297/303 | 0 | 0 |
| 100 | warm | 0 [0~0] | 0 | 300/0 | 0 | 0 |
| 500 | off | 328 [315~359] | 1002 | 0/0 | 0 | 0 |
| 500 | cold | 1 [1~1] | 3 | 1497/385 | 0 | 0 |
| 500 | warm | 0 [0~0] | 0 | 1500/0 | 0 | 0 |

최종 27개 wave 각각에서 기록된 Redis `evicted_keys` 차이가 0인지 검증했다. 이는 해당 측정 구간의 관측이며 모든 운영 부하에서 eviction이 없다는 보장은 아니다.

Redis 통계는 서버 전체 keyspace 카운터 차이다. 단일 요청에서 double-check로 여러 GET이 발생할 수 있고 측정 준비 명령이 일부 포함될 수 있어 API 요청 수와 일치하지 않는다. 캐시 경고 수는 측정 구간 앱 로그의 `Event list cache ` 문자열 출현 수이며 장애 횟수와 같은 의미가 아니다.

## 응답 동일성

- 모든 HTTP 200 측정 응답 5,234개는 SHA-256 `02437471778282b4b56bbc8907b71e7e7691f79d3f5176e0ab75e157f1bdb888`와 1,152,258바이트를 공유했다.
- 저장 fixture에는 서로 다른 이벤트 ID 3,500개가 있다. wire 응답은 약 1.15MB이며 캐시 적용 후에도 이 전체 본문을 계속 전송한다.
- `response.json`은 파싱 후 들여쓰기한 fixture다. compact UTF-8로 재직렬화한 SHA-256은 `02437471778282b4b56bbc8907b71e7e7691f79d3f5176e0ab75e157f1bdb888`이며 wire 해시·길이와의 일치 여부는 `true`다.
- Redis에는 완성된 UTF-8 응답 JSON을 저장한다. 성능 차이는 DB 조회 생략과 요청마다 반복하던 JSON 직렬화 생략을 함께 포함한다. Redis 네트워크 전송과 동시 요청 제어 비용도 포함된 종합 결과다.

## TTL·무효화·필터·장애 통합 점검

- 적재 직후 TTL 29,803ms, 만료 뒤 키 제거와 다음 요청의 기록된 digest 차이 1을 확인했다.
- 관리자 이벤트 수정이 커밋된 뒤 키가 제거되고 다음 전체 목록에 바뀐 이름이 보였다.
- `category=musical` 필터 응답 1,000개가 모두 해당 카테고리여서 전체 목록 캐시와 섞이지 않았다.
- Redis 중단 중 HTTP 200·동일 본문을 확인했다. 해당 단일 fallback 요청은 3062.83ms였다. Redis 재시작 후 캐시 키 재생성도 확인했다.
- 이 통합 시나리오는 한 번 실행했다. 관리자 생성·삭제·롤백 범위의 자동 테스트 결과는 별도 테스트 근거로 확인해야 한다.

## 자동 테스트 근거

저장된 테스트 결과 298개 중 295개 통과, 실패 0개, 오류 0개, 건너뜀 3개다. 건너뛴 테스트는 통과에 포함하지 않았다. 근거: `tests.json`.

## 해석의 한계

- cache miss 조정은 단일 JVM 안에서만 한다. 여러 앱 인스턴스의 동시 miss에 대한 분산 잠금이나 검증 결과는 없다.
- 세 번의 반복과 고정 블록 순서이며 CPU 스케줄링·Docker·호스트 상태 영향을 분리하지 못했다. 평균적인 운영 SLA나 AWS 성능으로 일반화하지 않는다.
- 각 wave를 재시작하고 예열했으므로 장시간 지속 부하·키가 많은 상황·자주 수정되는 이벤트·반복적인 Redis 장애는 측정하지 않았다.
- 약 1.15MB의 응답 전송, 추가 Redis 서비스 자원, 30초까지의 TTL 기반 최신성 한계는 남는다. 외부 SQL 수정은 앱의 after-commit 무효화 훅을 통과하지 않는다.
- 리소스 수치는 컨테이너에 설정한 제한이다. 저장된 모니터 표본은 앱·DB 중심이므로 Redis 실제 CPU·메모리 사용량이나 비용 절감을 입증하지 않는다.
- 무오류 로그나 단일 장애 복구 성공만으로 모든 운영 장애가 해결됐다고 주장하지 않는다.

근거 파일: `run_redis.py`, `results/method.json`, `results/environment.json`, `results/*-r*.json`, `results/*-r*.log`, `results/response.json`, 통합 점검이 실행된 경우 `results/integration.json`. 상세 수치는 `summary.json`과 `summary.csv`에 저장했다.

## 로컬 실행

로컬 Redis만 `backend-redis-1`로 실행했으며 `127.0.0.1:6379`에서 PONG/healthy를 확인했다. 백엔드 Compose는 캐시가 자동 활성화되며 IDE 실행은 `EVENT_LIST_CACHE_ENABLED=true`를 설정한다. 운영 배포는 이 측정 단계에서 수행하지 않았다.
