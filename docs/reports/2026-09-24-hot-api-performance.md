# WHAT'S HOT API 성능 측정

> 작성일 당시의 측정·검증 기록이다. 본문의 `artifacts/…` 경로에 있던 원시 데이터(CSV, 로그, 측정 스크립트)는 용량 때문에 저장소에 포함하지 않았고, 서버 주소는 `<EC2 주소>`로 가렸다.

측정일: 2026-09-24. 대상은 `GET /api/events/whats-hot`이며, 사용자 1명이 해당 화면을 한 번 열어 HOT 요청 1건을 보낸다고 가정했다. 각 시험에서 총 10,000건을 호출하고, 동시에 요청을 보내는 작업자 수를 100·1,000·10,000으로 바꿨다. 마지막 조건은 **1만 명의 브라우저 이용을 재현한 것이 아니라 1만 개의 API 요청을 가능한 한 동시에 시작하는 극한 시험**이다.

## 측정 조건

- 백엔드 이미지: `backend-backend:latest` (`sha256:28174cd87efe38fed22d791da08e35efa486345a8927f4d9ad4a745fd38e347b`), Java 21, Spring Boot 4.1.0. MySQL 8.0.46.
- Docker 환경: 12 CPU, 사용 가능 메모리 약 15.4 GiB. 기존 서비스와 분리된 측정용 백엔드와 세 개의 측정용 DB를 사용했다. 측정용 백엔드는 데이터 세트마다 재시작했고, SQL 출력 및 상세 로그와 결제 복구 작업을 껐다.
- 부하 생성기: 같은 Docker 네트워크의 별도 Java 21 컨테이너. 공유 `HttpClient`의 HTTP/1.1 연결을 사용해 작업자마다 응답을 받으면 다음 요청을 보냈다. 요청 사이 대기 시간은 없다. 연결 제한 시간 5초, 요청 제한 시간 15초다. 각 API는 본 측정 전 1,000건 이상 예열했다.
- 성공은 HTTP 200이다. 지연 시간의 p50·p95·p99는 **성공한 요청만** 대상으로 하며, 처리량은 `성공 요청 수 ÷ 전체 시험 시간`이다. 각 표의 본 측정은 조건별 1회다.
- Windows 호스트에서 Docker로 포트 전달을 거치는 예비 시험은 높은 부하에서 포트 자체가 지연되어 제외했다. 아래 결과는 모두 Docker 내부 네트워크에서 측정했다.

## 해석

홈 화면 HOT은 동시 작업자 100개에서 이벤트가 96→500→1,000개로 늘 때 p95가 **119→343→641ms**로 증가했다. 1,000개 세트에서는 동시 작업자를 100→1,000개로 늘려도 성공 처리량은 약 **399→416 req/s**로 거의 늘지 않았고, p95는 **641ms→3.58초**로 증가했다. 이 환경에서 1만 개를 한꺼번에 시도하는 조건은 안정적으로 처리되지 않았다.

카테고리 조건은 대상 이벤트를 줄여 전체 HOT보다 빨랐다. 다만 카테고리 화면은 실제로 이벤트 목록과 주간 랭킹 API도 함께 호출하므로, 위 수치는 **HOT API 단독 성능**이다.

로컬 Docker의 CPU·메모리와 부하 생성기가 같은 컴퓨터를 사용한다. 각 조건도 한 번씩 실행했으므로 이 수치를 운영 환경의 수용 인원으로 환산할 수 없다. 96개·동시 100개 조건을 재실행했을 때 p95는 119~148ms 범위였다. 다음 개선 단계에서는 생성된 SQL의 `EXPLAIN ANALYZE`와 DB 시간을 확인해, 판매량 합산·순위 계산 및 카테고리 조회 중 어느 구간이 실제 비용을 만드는지 분리해야 한다.

측정용 백엔드 컨테이너는 종료했다. 재측정할 수 있도록 `hot_bench_96`, `hot_bench_500`, `hot_bench_1000` DB는 유지했다. 원본 `free_ticket` DB는 측정 후에도 이벤트 96개·티켓 163개였다. 원본 API는 Docker 내부와 `127.0.0.1:8080`에서 HTTP 200을 반환한다. 이 환경에서는 `localhost`가 IPv6 `::1`로 연결될 때 응답이 지연되어, 호스트에서 접속할 때는 `127.0.0.1`을 사용해야 한다.

## 실행 계획 추가 분석

후속 분석에서는 MySQL Performance Schema에 남은 실제 HOT SQL 형태를 확인한 뒤, 측정용 DB에서 파라미터를 대입해 `EXPLAIN ANALYZE`를 실행했다. 애플리케이션 코드는 변경하지 않았다.

실제 처리 순서는 **이벤트 전체 조회 → 이벤트별 티켓 인덱스 조회 → 판매량 집계용 임시 테이블 → 판매량 정렬 → DENSE_RANK 계산 → 임시 테이블 및 최종 정렬 → LIMIT 7**이다. 1,000개 세트에서는 이벤트 1,000개에 대해 티켓 인덱스 조회가 반복되고, LEFT JOIN 결과 2,217행을 집계해 이벤트 1,000개 전체의 순위를 계산한 후 7개를 반환했다. 이 반복은 하나의 SQL 내부 조인 작업이며 애플리케이션의 N+1 쿼리는 아니다.

`tickets(event_id)`에는 이미 외래키용 인덱스가 있고 실제로 사용된다. 동일한 단일 컬럼 인덱스를 추가할 이유는 없다. 이벤트 전체를 대상으로 하는 홈 HOT에서는 `events(category)` 인덱스도 전체 집계 자체를 없애지 못한다.

### SQL 후보 비교

후보는 **순위 계산 중에는 이벤트 ID·판매량·순위만 유지하고, 상위 7개를 고른 뒤 이름·위치·이미지 등 상세 필드를 읽는 방식**이다. 전체 이벤트의 집계와 순위 계산은 여전히 수행한다.

기존 SQL과 후보를 번갈아 6회씩 실행하고 각 첫 회를 제외한 5회의 중앙값을 비교했다. 아래 시간은 부하가 없는 상태의 `EXPLAIN ANALYZE` 최상위 실행 시간이며, 앞 표의 HTTP p95와는 다른 지표다.

| 이벤트 | 기존 SQL 중앙값 | 후보 SQL 중앙값 | 감소율 |
|---:|---:|---:|---:|
| 96 | 0.685 ms | 0.444 ms | 35.2% |
| 500 | 3.410 ms | 1.870 ms | 45.2% |
| 1000 | 7.210 ms | 3.770 ms | 47.7% |

1,000개 세트에서 기존 SQL의 5회 결과는 7.21·8.64·7.17·7.20·8.13ms, 후보는 4.01·3.56·3.77·4.49·3.44ms였다. 후보 실행 계획에서도 전체 1,000개를 집계하지만, 상세 이벤트 행의 최종 PK 조회는 7회다. 이는 상세 필드를 임시 테이블·정렬 과정에 함께 유지하는 비용을 줄이는 방향이 유효함을 보여준다. API 처리량·응답 시간이 같은 비율로 개선된다는 뜻은 아니다.

비교한 후보 SQL:

```sql
SELECT r.rnk, e.id, e.name, e.start_date, e.end_date,
       e.location, e.banner_image_url, e.main_image_url, e.category
FROM (
    SELECT e.id,
           DENSE_RANK() OVER (
               ORDER BY COALESCE(SUM(t.sold_ticket), 0) DESC
           ) AS rnk,
           COALESCE(SUM(t.sold_ticket), 0) AS score
    FROM events e
    LEFT JOIN tickets t ON t.event_id = e.id
    WHERE (NULL IS NULL OR NULL = e.category)
    GROUP BY e.id
    ORDER BY score DESC
    LIMIT 7
) r
JOIN events e ON e.id = r.id
ORDER BY r.score DESC;
```

### 결과 동일성과 다음 적용 조건

96·500개 세트에서는 기존과 후보의 순위·ID·상세 필드·순서가 모두 일치했다. 1,000개 세트에서는 1위 동점 이벤트가 7개보다 많아 선택된 ID가 달랐다. 기존 SQL이 판매량만 정렬하고 동점 순서를 지정하지 않기 때문이다. 비교용으로 두 SQL 모두 판매량 다음에 이벤트 ID 오름차순을 적용하자 세 세트의 7개 결과와 상세 필드가 모두 일치했다. 실제 적용 시에는 이 동점 기준을 명시하고 카테고리·빈 결과·티켓 없는 이벤트도 검증해야 한다.

카테고리 검증용 `SELECT DISTINCT category`의 단발 실행 시간은 96·500·1,000개에서 약 0.048·0.155·0.412ms였다. 전체 HOT 요청에는 이 쿼리가 실행되지 않으므로 홈 HOT 개선의 첫 대상은 판매량 집계 SQL이다.

현재 확인된 것은 **DB 집계 비용이 데이터 규모에 따라 증가하고, 상세 필드를 늦게 읽는 후보가 그 비용을 줄인다**는 점이다. HTTP 지연에는 연결·서버 처리·DB 연결 대기 등도 포함되므로 이번 분석만으로 모든 지연을 SQL 탓으로 확정하지 않는다. 다음 적용 단계는 동점 기준을 포함해 후보를 애플리케이션에 반영하고, 같은 데이터와 부하 조건으로 API를 다시 측정하는 것이다.

## 후보 적용 및 전체 API 재측정

위의 SQL 후보와 다음 적용 조건은 **적용 전 분석 기록**이다. 이후 HOT 쿼리를 변경했다. 판매량 내림차순을 먼저 적용하고, 동점이면 `events.end_date` 오름차순, 종료일도 같으면 이벤트 ID 오름차순으로 정렬한다. 마지막 ID 기준은 동일한 종료일에서 `LIMIT` 결과를 안정적으로 만들기 위한 것이다. `DENSE_RANK`는 판매량만으로 계산하므로 판매량 동점은 같은 순위를 유지한다. 순위 계산에서는 ID·종료일·판매량·순위만 다루고, `LIMIT`으로 고른 이벤트의 상세 필드를 마지막에 읽는다.

### 결과 검증

원래 SQL에도 합의한 동점 정렬 기준을 적용해 새 SQL과 비교했다. 96·500·1,000개 데이터 세트 각각에서 홈 `limit=7`과 `musical` 카테고리 `limit=5`의 **6개 결과 모두** 순서, 순위, ID, 이름, 시작일, 종료일, 장소, 배너·메인 이미지 URL, 카테고리가 정확히 같았다. 새로 빌드한 백엔드의 실제 HTTP JSON도 이 6개 기준 결과와 일치했다. 티켓이 없는 이벤트보다 판매량이 있는 이벤트가 우선하고, 판매량이 같은 이벤트의 종료일·ID 정렬 및 공동 순위를 검증하는 Repository 테스트와 백엔드 전체 테스트도 통과했다.

이는 **새로 정한 동점 기준을 적용한 기존 SQL과 결과가 같다**는 뜻이다. 이전 SQL은 동점의 순서를 정의하지 않았으므로, 그 실행에서 우연히 선택되던 동점 이벤트 ID까지 같다는 뜻은 아니다.

이벤트 1,000개·동시 작업자 100개 조건에서 p95는 **641.08→247.98ms**, 성공 처리량은 **398.6→1,015.9건/초**였다. 96개 조건의 p95 감소는 작고 p99는 오히려 증가했다. 원래 측정의 SQL은 새 동점 정렬 기준이 없었으므로 두 열은 엄밀한 SQL 한 부분만의 A/B 비교는 아니다. 또한 각 조건을 한 번씩 실행했고 DB·부하 생성기·백엔드가 같은 로컬 컴퓨터의 자원을 공유한다. 따라서 개선 폭을 운영 환경의 보장치나 동시 접속 가능 인원으로 해석할 수 없다. 카테고리 HOT의 변경 후 HTTP 성능과 변경 후 동시 작업자 10,000개 조건은 측정하지 않았다.

## 동일 정렬 기준 A/B 재측정

위 단발 비교의 한계를 줄이기 위해 두 JAR를 별도로 준비했다. **기존 방식**은 이벤트 전체 상세 필드를 조인·집계·순위 계산에 사용하며 `판매량 DESC, events.end_date ASC, events.id ASC`로 정렬한 뒤 `LIMIT`을 적용한다. **변경 방식**은 같은 정렬과 순위를 사용하되, ID·종료일·판매량으로 상위 항목을 고른 다음 상세 필드를 읽는다. 두 빌드의 `src/main` 차이는 HOT Repository 쿼리 한 곳뿐이다.

각 데이터 세트마다 두 측정 서버를 동일한 DB에 연결했다. Docker 내부의 같은 Java 부하 생성기에서 서버별 1,000건을 예열한 뒤, **총 10,000건·동시 작업자 100개**를 기존→변경→변경→기존→기존→변경 순서로 3회씩 측정했다. 요청 사이 대기는 없고 HTTP 200만 성공으로 집계했다. 각 실행은 모두 **10,000/10,000건 성공**했다. p50·p95·p99와 처리량은 각각 세 실행의 중앙값이다.

**판단:** 같은 정렬 기준으로 다시 비교해도 변경 방식의 p95와 처리량이 세 데이터 규모 모두에서 개선됐다. 다만 이벤트 1,000개의 p95 감소는 앞 절의 단발 비교 61.3%가 아니라 이번 반복 비교에서 **14.1%**다. 첫 실행과 마지막 실행의 지연 차이가 커서 JIT 예열이나 로컬 자원 변동의 영향이 남아 있다. 운영 환경의 절대 응답시간이나 동시 접속 수용량은 이 측정으로 확정할 수 없다. 변경의 방향성은 일관되지만 개선 폭은 이번 동일 기준 반복 측정값을 우선해 해석한다.

## 예상 방문자 유입 시험: 최대 1만 명이 거의 동시에 접속

사용자는 최대 1만 명이 **거의 동시에 접속**할 수 있다고 가정했다. 현재 홈페이지 코드는 페이지 진입 시 `GET /api/events/whats-hot?limit=7`을 한 번 요청한다. 이를 바탕으로 **1만 명 모두 홈페이지에 접속해 HOT 요청을 각 1건 보낸다**고 모델링했다. 데이터는 이벤트 1,000개·티켓 1,721개 측정 DB, 서버는 변경 SQL을 담은 JAR다. Docker 내부 부하 생성기는 요청을 지정한 시간에 고르게 시작하도록 예약하고, 예정 시각부터 응답 완료까지의 지연을 기록했다. 본 시험 전에 서버에 1,000건을 보내 예열했다.

| 1만 명 유입 시간 | 예정 요청률 | 성공/10,000 | 부하 생성기 발송 지연 p95 | HOT 응답 p95 | HOT 응답 p99 | 최대 진행 중 요청 |
|---:|---:|---:|---:|---:|---:|---:|
| 20초 | 500건/초 | 10,000 | 0.1 ms | 10.0 ms | 27.3 ms | 66 |
| 15초, 1회 | 약 667건/초 | 10,000 | 1.4 ms | 33.6 ms | 79.6 ms | 77 |
| 15초, 재실행 | 약 667건/초 | 10,000 | 0.1 ms | 8.1 ms | 56.8 ms | 101 |
| 10초, 1회 | 1,000건/초 | 10,000 | 5.6 ms | 1,324.4 ms | 1,862.9 ms | 855 |
| 10초, 재실행 | 1,000건/초 | 10,000 | 4.2 ms | 589.3 ms | 1,078.1 ms | 419 |
| 1초 | 10,000건/초 | 9,375 | 960.7 ms | 8,498.4 ms | 8,858.5 ms | 8,839 |

1초 시험의 나머지 **625건은 HTTP 응답 코드가 아닌 클라이언트 예외**였다. 부하 생성기가 요청을 모두 시작하는 데 실제로 약 **2.01초**가 걸렸으므로 정확한 1초 유입을 재현하지 못했다. 이 조건의 지연 통계는 성공한 9,375건만 포함하며, 실패 원인을 서버로 단정할 수 없다. 측정 서버와 부하 생성기 컨테이너에는 메모리 부족 종료가 없었고 서버 로그에도 관련 오류가 기록되지 않았다.

**판단:** 이 로컬 환경에서 1만 명이 10초 안에 홈페이지에 들어오면 HOT p95가 두 번 모두 **300ms를 넘었다**. 15초 유입에서는 두 번 모두 300ms 아래였지만, 이 숫자를 운영 환경의 안전 한계로 사용할 수는 없다. 카테고리 화면은 HOT 외에 이벤트 목록과 주간 랭킹 API를 동시에 호출하므로 이 시험보다 서버 부하가 커질 수 있다. 실제 수용량을 정하려면 배포 환경의 자원과 피크 방문 분포를 기준으로 화면 전체 요청을 측정해야 한다.

## 집중 요청 실패 원인 재현 진단 — 2026-09-25

앞 시험의 625건은 예외 유형을 남기지 않아 소급해서 원인을 확정할 수 없다. 같은 변경 JAR·1,000개 이벤트 DB에서 1,000건 예열 후 1만 건을 1초에 시작하도록 재현하고, 이번에는 클라이언트 예외 유형, 서버 접근 로그, TCP 대기열 카운터를 수집했다. 진단용 접근 로그를 추가했으므로 이 실행은 이전 성능값과 직접 비교하는 용도가 아니다.

| 재현 결과 | 건수 | 확인된 의미 |
|---|---:|---|
| HTTP 200 | 9,235 | 클라이언트가 정상 응답을 받음 |
| `HttpConnectTimeoutException: HTTP connect timed out` | 590 | 연결 수립이 설정한 5초 제한을 넘김 |
| `HttpTimeoutException: request timed out` | 175 | 요청이 설정한 20초 제한 안에 끝나지 않음 |

서버 네트워크의 `ListenOverflows`와 `ListenDrops`는 각각 **0→5,521**로 증가했다. 집중 요청 도중 서버 TCP 연결 대기열이 포화되어 연결 패킷을 버린 사실이 확인됐다. 이 카운터에는 재전송 등이 포함될 수 있으므로 5,521명을 뜻하지 않는다. 서버 접근 로그에 기록된 10,382건(예열 1,000건 포함)은 모두 HTTP 200이었으며, 서버 로그에는 관련 예외가 없었다. 따라서 확인된 실패 유형은 HTTP 500이나 SQL 실행 오류가 아니라 **연결 또는 요청의 시간 초과**다. 연결 대기열 포화는 직접 확인했지만, 요청 시간 초과 175건이 서버 내부 대기·처리·전송 중 어느 부분에서 지연됐는지는 이 자료만으로 나눌 수 없다.

부하 생성기의 실제 발송 구간은 약 2.11초, 예정 시각 대비 발송 지연 p95는 약 1.06초였다. 부하 생성기 역시 1초 발송 목표를 지키지 못했으므로, 이 결과를 운영 서버의 정확한 1초 동시 접속 한계로 해석하지 않는다. 같은 로컬 머신에서 요청이 집중될 때 **연결 대기열 포화와 시간 초과가 함께 발생하는 현상**을 재현한 것이다.

## 연결 실패 원인 분리 진단 — 2026-09-25

### 실제 설정과 부하 중 상태

JMX로 실행 중인 서버의 값을 직접 읽었다. 아래 값은 연결 관련 설정을 별도로 지정하지 않은 측정 서버에서 확인한 값이다.

| 항목 | 실제 값 | 의미 |
|---|---:|---|
| Tomcat `maxConnections` | 8,192 | 동시에 받아들여 유지하는 연결 수 제한 |
| Tomcat `acceptCount` | 100 | 새 연결을 기다리게 하는 OS 접속 대기열의 요청 설정값 |
| Tomcat `keepAliveTimeout` | 60,000 ms | 응답 후 다음 요청을 기다리며 연결을 유지하는 시간 |
| Tomcat `maxThreads` | 200 | 요청 처리 스레드 수 제한 |
| Hikari `MaximumPoolSize` | 10 | DB 연결 수 제한 |
| Hikari `ConnectionTimeout` | 30,000 ms | DB 연결을 빌리기 위해 기다리는 제한 시간 |
| 부하 생성기 연결/요청 제한 | 5초 / 20초 | 연결 또는 응답을 기다리다 실패로 처리하는 시간 |

이 제한의 의미는 [Tomcat HTTP Connector 공식 설명](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html)과 일치한다. 최대 연결 수에 도달하면 추가 연결이 OS 대기열에서 기다리고, 대기열까지 차면 연결 거절이나 시간 초과가 발생할 수 있다.

원래 설정의 첫 집중 시험에서는 약 5초부터 연결 수가 **8,192개에 고정**됐다. 처리 중에는 요청 스레드 200개, 활성 DB 연결 10개, DB 연결 대기 스레드 최대 190개가 관측됐다. 특히 **12~16초에는 처리 중인 스레드와 활성 DB 연결이 모두 0인데도 연결 수가 8,192개로 유지**됐다. 이미 응답한 연결이 다음 요청을 기다리면서 슬롯을 차지해, 서버가 쉬어도 새 연결을 받아들이지 못하는 상태였다.

### 설정 하나를 바꾼 비교

앱 코드와 SQL은 그대로 두고 임시 측정 서버의 `maxConnections`만 변경했다. 실패한 비교도 아래에 함께 남겼다.

| 시험 | 최대 연결 수 | 성공 | 연결 시간 초과 | 요청 시간 초과 |
|---|---:|---:|---:|---:|
| 원래 설정 `baseline` | 8,192 | 9,520 | 223 | 257 |
| 연결 수만 상향 `connections20k` | 20,000 | 10,000 | 0 | 0 |
| 같은 서버에서 원래 값 복원 `baseline-repeat` | 8,192 | 9,479 | 383 | 138 |
| 같은 서버에서 다시 상향 `connections20k-repeat` | 20,000 | 8,162 | 1,838 | 0 |
| 새 생성기 `fresh20k` | 20,000 | 10,000 | 0 | 0 |
| 생성기 초기화 후 `reset20k` | 20,000 | 10,000 | 0 | 0 |

`connections20k-repeat`에서는 서버 연결 수가 최대 7,634개였지만 생성기가 1만 건을 발송하는 데 약 **12.78초**가 걸렸다. 따라서 모든 실패를 8,192개 연결 제한 하나로 설명하거나, 20,000으로 높이면 항상 성공한다고 주장할 수 없다. 이 시험의 생성기/네트워크 측 원인은 별도로 남는다.

추가 원래 설정 시험 `baseline-timed`에서는 연결 수 표본의 최대값이 7,976개였고 연결 시간 초과 237건이 발생했다. 서버 `ListenOverflows`와 `ListenDrops`는 각각 2,861회 증가했으며, 실패한 237건은 요청 ID가 서버 접근 로그에 없었다. **최대 연결 수에 오래 막히는 현상 외에, 순간적인 접속 대기열 넘침도 존재**한다. 대기열 카운터는 패킷/재전송 등에 대한 값이며 실패한 사람 수와 같지 않다.

### CPU·DB 부하 없이 실패 원인을 재현한 시험

대량 요청의 자원 경쟁을 제거하기 위해, 임시 서버의 최대 연결 수를 4개로 낮추고 서로 다른 HTTP 클라이언트 4개가 HOT 응답을 정상적으로 받은 뒤 연결을 유지하게 했다. 각 시험 후 원래 값으로 복원했다.

1. **슬롯 해제 시험:** 다섯 번째 요청은 서버 처리 스레드 0개·활성 DB 연결 0개 상태에서도 완료되지 않았다. 기존 연결 하나를 닫자 HTTP 200으로 완료됐다.
2. **요청 시간 초과 시험:** 연결을 비우지 않고 그대로 두자, 처리 스레드·활성 DB 연결이 계속 0인 상태에서 `HttpTimeoutException: request timed out`이 발생했다. 이 작은 재현에서는 요청 제한을 3초로 사용했다.
3. **접속 대기열 시험:** 같은 4개 연결을 유지하고 추가 TCP 연결을 만들었다. `acceptCount=100` 상태에서 추가 연결 101개가 TCP 연결을 완료한 후 다음 연결은 `SocketTimeoutException: Connect timed out`으로 실패했다. 이때도 처리 스레드와 활성 DB 연결은 0이었다. 이 재현의 TCP 연결 제한은 500ms였다.

이 세 시험은 **응답이 끝난 keep-alive 연결의 슬롯 점유 → 새 요청 수신/처리 대기 → 접속 대기열 포화 또는 요청 기한 초과**라는 실패 경로를 직접 검증한다. 컴퓨터의 CPU나 메모리가 부족해야만 생기는 현상이 아니다. 서버의 연결 수/대기열 제한과 연결 유지 정책만으로도 같은 유형의 실패를 만들 수 있다.

### 추가로 관측된 지연과 해석 범위

- **DB 연결 대기:** 처리 스레드 200개 중 최대 약 190개가 DB 연결 10개를 기다렸다. 응답 지연을 만드는 대기 지점은 확인됐지만, DB 연결 수를 늘리는 것이 최선인지는 별도 판단이 필요하다. DB 연결풀 시간 초과나 SQL 예외를 실패 원인으로 확인한 것은 아니다.
- **부하 생성기 변동:** 최대 연결 수 20,000 조건에서 같은 생성기의 연속 3회 실행은 발송 구간이 약 3.50→7.39→16.96초로 늘었고, 세 번째는 181건이 실패했다. 생성기에서 관측한 TIME_WAIT 소켓은 실행 시작 시 약 0→8,466→14,713개였으며 마지막 실행에서 생성기 CPU 사용률도 크게 높아졌다. 잔여 소켓과 생성기 CPU 부담이 동반됐지만, 커널 수준 추적 없이 TIME_WAIT를 유일한 원인으로 확정하지 않는다. 이후 초기화 시험 전에는 중단 시간이 끼어 TIME_WAIT가 이미 0이었으므로, 회복을 초기화만의 효과로 단정하지 않는다.
- **원래 625건:** 첫 시험은 예외별 기록이 없으므로 각각의 원인을 소급 확정할 수 없다. 이후 진단에서 동일 유형의 실패 경로와 실제 병목 상태를 확인한 것이다.

**진단 결론:** 서버 측에서 직접 확인한 실패 경로는 **유지 중인 연결에 의한 최대 연결 수 도달 및 TCP 접속 대기열 넘침**이다. 응답 후에도 60초 동안 연결 슬롯이 유지될 수 있는데 클라이언트는 연결 5초·요청 20초 만에 포기하므로, 처리할 CPU·DB 여유가 생겨도 일부 요청이 실패할 수 있다. 별도로 DB 연결 대기와 생성기 지연이 측정값에 영향을 주었다. 따라서 SQL 최적화나 AWS 이전만으로 모든 실패가 사라진다고 결론 낼 수 없다.

원시 요청 결과, JMX 시계열, TCP 카운터, 접근 로그, 재현 코드는 `artifacts/hot-diagnosis/`에 보존했다. 계측용 JMX는 외부 포트를 공개하지 않은 임시 Docker 서버에서만 켰다. 운영 앱 소스·설정에는 이 진단용 연결 수 변경을 적용하지 않았다.

### 같은 요청률에서 경로 비교

새 측정 서버를 시작해 DB 연결 풀이 실제 10개(`TotalConnections=10`, `MaximumPoolSize=10`)임을 확인한 후 각각 새 부하 생성기로 15,000건을 10초에 발송했다.

MySQL 성능 계측에서 HOT SQL의 마지막 비교 실행 평균은 약 **6.00ms**였고, 상세 조회의 두 SQL은 전체 누적 기준 각각 약 **0.03ms, 0.08ms**였다. 두 경로의 응답 본문과 서버 작업도 다르므로 이 수치만으로 지연 차이 전체를 SQL에 귀속하지 않는다.

### DB 연결 수만 늘린 시험과 판단

별도 재시작 전 시험에서 JMX로 Hikari 최대 연결 수만 10→20으로 바꿨다. 같은 1,500건/초에서 HOT p95는 **1,157.5→1,507.8ms**, HOT SQL 평균은 **5.88→7.90ms**였다. 서버와 생성기를 포함한 로컬 자원 상태가 실행 사이 변했고, 20→10으로 되돌려도 이미 열린 연결이 즉시 10개로 줄지 않아 그 반복 시험은 깨끗한 A/B가 아니다. **연결 수를 20개로 늘려도 개선을 확인하지 못했다**는 범위까지만 해석한다.

**결론:** 이벤트 1,000개 HOT 조회는 이 환경에서 700건/초까지의 시험에서 응답 p95가 18ms 미만이었고, 1,000건/초에서는 153ms, 1,500건/초에서는 1.16초 이상으로 증가했다. 1,500건/초에서 DB 연결 대기와 Tomcat 작업 스레드 포화가 지속되어 HOT 계산 비용을 낮추면 개선 여지가 있다. 다만 실패는 없었고, 부하 생성기와 서버가 같은 로컬 머신에 있어 운영 환경의 최대 수용량이나 DB 서버 자체의 한계는 아직 확정할 수 없다. 이벤트 판매량 합계 컬럼을 추가하는 쓰기 비용을 감수하기 전에, 동일 응답을 짧게 캐시하는 방식으로 HOT SQL 실행 횟수를 줄이는 실험이 더 작은 다음 단계다.

원시 자료는 `artifacts/hot-diagnosis/bottleneck-20260925-*` 파일에 있다. 기존 96개 이벤트 DB와 앱 코드는 이 시험에서 수정하지 않았다.

## HOT 5초 로컬 캐시 적용과 전후 비교 — 2026-09-25

`EventController.whatshot`에서 `category + limit`를 키로 `WhatsHotResponse`를 5초 보관한다. 캐시 적중 시 `EventService`의 읽기 트랜잭션에 들어가지 않는다. 만료 후 같은 키로 동시에 요청하면 `ConcurrentHashMap.compute` 안에서 한 요청만 계산하고 다른 요청은 그 결과를 받는다. 이 캐시는 **앱 인스턴스별**이며, 서버를 여러 대 실행하면 인스턴스마다 처음 한 번 계산한다. 결과 갱신은 판매 완료 후 최대 약 5초 늦을 수 있다.

### 캐시가 비어 있을 때 1만 건 집중 요청

새 캐시 서버에서 이벤트 상세 조회로 앱만 예열한 뒤, 홈 HOT 키가 빈 상태에서 10,000건을 1초에 시작하도록 예약했다. 생성기가 실제 발송을 마치는 데 **2.635초**, 발송 지연 p95는 **1,486ms**가 걸려 정확한 1초 유입을 재현하지 못했다. **9,930건 성공, 70건 연결 시간 초과**였고 성공 요청의 응답 p95는 3,296.9ms였다. 이때 HOT SQL은 **정확히 1회** 실행됐고, JMX 표본의 DB 연결 대기는 0이었다. 최대 서버 연결 수는 7,897개였다. 서버 네트워크의 시험 후 `ListenOverflows`/`ListenDrops`는 각각 4,090이었으며, 실패한 70개 요청 ID는 접근 로그에 없었다. 이 카운터는 실패한 이용자 수가 아니고 시험 전 표본을 남기지 않았으므로 증가량으로 해석하지 않는다. 서버에 도착한 요청의 처리 시간 p95는 약 39.2ms였다.

**판단:** 같은 HOT 결과를 반복 계산하지 않는 캐시는 이 데이터와 부하에서 DB 작업을 크게 줄이고 DB 연결 대기를 없앴다. 그러나 빈 캐시에서도 1만 건 집중 요청 중 70건은 서버에 도착하기 전에 연결 시간 초과로 실패했다. HOT 조회 비용과 대규모 동시 접속 수용량은 별도 과제로 남는다. 결과는 로컬 한 대의 앱·DB·부하 생성기 환경에 한정된다.

원시 요청/JMX 자료는 `artifacts/hot-diagnosis/cache-*`, DB 증분·접근 로그는 `artifacts/hot-cache-benchmark/`에 저장했다. 두 측정 JAR의 SHA-256은 본문에 기록했다. 원래 `free_ticket` 96개 이벤트 DB는 변경하지 않았다.

| 연결 유지 시간만 변경 | 8,192 / 100 / 1초 | 3.27초 | 9,187 | 4,702ms | 6,248 |
| 기본값 B | 8,192 / 100 / 60초 | 2.58초 | 10,000 | 2,809ms | 2,570 |
| 네 생성기 동기화·기본값 | 8,192 / 100 / 60초 | 3.23초 | 9,887 | 3,200ms | 6,355 |
| 네 생성기 동기화·대기열 2,048 | 8,192 / 2,048 / 60초 | 2.58초 | 10,000 | 1,857ms | 1,049 |

네 생성기 시험은 각각 2,500건을 같은 목표 시각에 시작하게 했다. 그러나 로컬 자원 경쟁 때문에 네 생성기를 합친 실제 발송도 1초 안에 끝나지 않았다. 위 모든 시험에서 HOT SQL은 각각 1회만 실행됐고 DB 연결 대기는 0이었다. 연결 유지 1초 시험의 실패 813건은 연결 시간 초과 802건과 응답 헤더를 받기 전 연결이 닫힌 예외 11건이었다. 최대 연결 20,000 시험은 연결 수 표본 최대가 7,087개였는데도 연결 시간 초과가 1건 발생했다.

`ListenOverflows`는 서버 TCP 접속 대기열의 패킷/재전송 계수이며 실패한 사용자 수가 아니다. 기본값 두 번 모두 HTTP는 전부 성공했지만 넘침은 각각 기록됐다. 대기열 2,048 단일 생성기 시험에서는 넘침이 0이었고, 네 생성기 시험에서는 1,049회가 남았다. **대기열 증가가 이 로컬 조건에서 가장 유망한 조정**이지만, 발송 속도와 호스트 상태가 실행마다 달라 정확한 개선 배율이나 무실패 보장을 산출할 수 없다. 최대 연결 수만 상향한 시험은 개선 근거가 없고, 연결 유지 시간을 1초로 줄인 시험은 결과가 악화됐다.

**결론:** HOT 캐시가 DB 작업을 제거해도 접속 수신 단계가 남는다. 이 컴퓨터에서는 부하 생성기 자체가 1만 건/1초 목표를 달성하지 못했으므로 **진짜 1초 유입의 수용량은 아직 미측정**이다. 별도 PC/VM이 생기면 동일한 설정과 외부 부하 생성기로 재시험하고, HOT 단일 API뿐 아니라 홈페이지의 전체 요청도 측정해야 한다. 이번 시험은 운영 설정을 변경하지 않았다.

재현 스크립트와 요청별 결과, JMX 표본, 설정 확인, 접속 대기열 전후 카운터는 `artifacts/hot-connection-experiments/`에 있다. 서버 접근 로그는 종료 직전 복사 시 버퍼링으로 일부 성공 요청이 빠져 있어 완료 건수 판정에는 클라이언트 요청 CSV를 사용했다.

## EC2 배포 서버 재측정 — 2026-09-25

대상은 `https://<EC2 주소>/api/events/whats-hot?limit=7`이다. 서버는 EC2의 Caddy → Spring Boot → MySQL이며, 부하 생성기는 별도 Windows PC에서 실행했다. 배포 DB는 시험 전 이벤트·티켓 0건이었다. 기존 로컬 측정 DB의 이벤트 1,000건·티켓 1,721건을 추출해 배포 DB에 적재한 뒤, 추가 이벤트·티켓을 지워 500건·859건 및 96건·163건 조건을 만들었다. 세 규모에서 API의 상위 7개 ID·순서가 기존 로컬 데이터와 같았고 한글 이름도 정상임을 확인했다. 처음 적재할 때 MySQL 클라이언트 문자셋을 지정하지 않아 한글이 깨진 탐색 시험은 아래 표에서 **제외**했다. UTF-8로 다시 적재한 뒤 세 규모를 모두 재측정했다.

각 조건은 HOT 캐시를 한 번 채운 뒤 JDK `HttpClient` HTTP/1.1 공유 클라이언트로 10,000건을 1초 안에 시작하도록 예약한 **단발 시험**이다. 연결 제한 시간 5초, 요청 제한 시간 20초, HTTP 200만 성공으로 집계했다. 응답시간 백분위는 성공한 요청만 대상으로 한다. `첫 1초 시작`은 첫 `sendAsync` 호출부터 1초 동안 호출을 시작한 건수이며, 실제 패킷이 서버에 도달한 건수가 아니다.

| 이벤트 / 티켓 | 성공 / 10,000 | 연결 시간 초과 | 로컬 포트 충돌 | 기타 실패 | 호출 시작 구간 | 첫 1초 시작 | 성공 p50 / p95 / p99 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 96 / 163 | 5,328 | 3,526 | 1,146 | 0 | 2.36초 | 1,862 | 5,507 / 7,122 / 7,510ms |
| 500 / 859 | 2,151 | 7,849 | 0 | 0 | 1.90초 | 1,821 | 9,850 / 10,903 / 11,015ms |
| 1,000 / 1,721 | 5,423 | 4,576 | 0 | 1 | 1.71초 | 3,244 | 5,530 / 6,349 / 6,919ms |

세 시험 모두 실제 호출 시작이 1초를 넘겼으므로 **1만 요청/1초의 서버 수용량을 검증하지 못했다**. 특히 96건 시험의 `BindException: Address already in use` 1,146건은 부하 생성 PC의 연결 자원 부족을 직접 보여준다. Windows의 TCP 동적 포트 범위는 49,152~65,535(총 16,384개)였고 시험 후 해당 서버로 향한 `TIME_WAIT` 연결도 관측됐다. 나머지 연결 시간 초과를 전부 로컬 PC 문제라고 단정할 수는 없다. 정상 데이터 시험에서 백엔드 컨테이너의 `ListenOverflows` 증분은 1,000건 조건 58, 500·96건 조건 0이었다. 이 카운터는 실패 사용자 수가 아니다. 세 규모의 성공률이 데이터 크기에 따라 일정하게 변하지 않은 점도 연결·생성기 변동이 큰 증거다.

캐시 효과는 별도로 확인됐다. 정상 데이터 시험 직전부터 종료까지 MySQL의 HOT 순위 SQL 누적 실행 횟수는 27→35회였다. 이 구간에는 시험용 30,000건 외에 응답 확인용 소수 요청도 포함된다. SQL 누적 시간은 0.123→0.160초였다. 따라서 이번 대량 실패를 매 요청의 HOT 집계나 DB 연결 부족으로 설명할 근거는 없다. 응답 실패는 클라이언트에서 연결 단계 예외로 기록됐고 HTTP 5xx는 없었다. 시험 직후 HOT API는 정상 응답했다.

문자셋 수정 전의 별도 탐색 시험에서는 EC2 외부 인터페이스에서 500·96건 조건 각각 고유 TCP SYN 10,000개를 관측했지만 약 2~3초에 걸쳐 도착했다. 이는 **연결 시도 도착**을 확인한 자료이며, 정상 데이터 시험의 HTTP 처리량 표에는 섞지 않았다. 브라우저의 페이지 자산 요청, 서로 다른 실제 이용자의 연결 재사용, 예매 흐름은 이번 시험 범위에 없다. 정확한 1만 명/1초를 판단하려면 충분한 발송 성능과 서로 다른 출발지 포트를 가진 부하 생성기를 추가하고 서버의 HTTP 요청 도착 시각도 함께 기록해야 한다.

원시 CSV·응답 JSON·서버 TCP 카운터·탐색 시험 패킷 기록·재현용 JDK 측정기는 `artifacts/hot-deployed-benchmark/`에 있다. 배포 DB의 시험 데이터는 모두 제거했고, 이벤트·티켓은 다시 0건, 기존 사용자 1건은 유지했다. 이벤트·티켓 자동 ID 시작값도 배포 전 스키마 값인 617·164로 복원했다. 로컬 측정 DB 컨테이너도 원래의 정지 상태로 돌려놓았다.

## k6로 배포 HOT 재측정 — 2026-09-25

같은 배포 API와 이벤트·티켓 데이터 1,000/1,721 → 500/859 → 96/163건을 사용했다. 별도 부하 생성기는 없어서 앞 절과 같은 Windows PC의 Docker에서 k6 v2.3.0을 실행했다. 각 조건은 `constant-arrival-rate` 10,000건/초를 1초간, 미리 준비한 가상 사용자 5,000명으로 시도했다. 응답 본문은 버리고 HTTP 200만 성공으로 셌다. HTTP 시간은 요청을 시작한 건에 대한 k6 측정치이며, 성공 응답 p95는 성공한 건에만 적용된다. 각 조건은 한 번씩 실행했다.

| 이벤트 / 티켓 | 목표 / 실행 요청 | k6가 보고한 누락 | HTTP 200 / 실행 요청 | 접속 거절 | 성공 HTTP p95 | 전체 반복 p95 |
|---:|---:|---:|---:|---:|---:|---:|
| 1,000 / 1,721 | 10,000 / 5,000 | 972 | 4,998 / 5,000 | 2 | 1,824ms | 9,188ms |
| 500 / 859 | 10,000 / 4,490 | 0 | 4,146 / 4,490 | 344 | 2,039ms | 6,088ms |
| 96 / 163 | 10,000 / 4,449 | 0 | 3,821 / 4,449 | 628 | 3,071ms | 7,372ms |

**세 조건 모두 1만 건/1초 유입을 생성하지 못했다.** `dropped_iterations`가 0인 두 조건도 실행 요청 수는 목표의 절반 미만이므로 누락 0을 목표 달성으로 읽으면 안 된다. 접속 거절은 `dial tcp <EC2 IP>:443: connect: connection refused`였고, HTTP 5xx 응답이 아니다. HTTP p95에는 연결·TLS 준비 시간이 모두 반영되지 않으므로 사용자가 체감할 전체 시간으로 해석하지 않는다. 규모가 작아지는데 실패가 증가한 결과는 이 단발 시험으로 이벤트 수의 영향을 추정할 수 없음을 보여준다. 데이터 변경 후 캐시 예열 상태도 동일하게 통제하지 않았다.

### 지연이 발생한 단계

| 이벤트 수 | 접속 준비 `blocked` p95 | TCP 연결 p95 | TLS 준비 p95 | 첫 바이트 대기 p95 | 전체 반복 p95 |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 8,450ms | 7,668ms | 2,973ms | 1,557ms | 9,188ms |
| 500 | 5,767ms | 3,952ms | 2,384ms | 1,330ms | 6,088ms |
| 96 | 7,284ms | 7,220ms | 3,142ms | 1,803ms | 7,372ms |

가장 큰 지연은 HTTP 요청을 보내기 전의 **연결 수립 구간**에 있다. 첫 바이트 대기도 1초를 넘으므로 프록시·앱·네트워크의 응답 경로에 추가 대기가 있었다. 이 값들은 각 단계의 독립적인 p95이며 같은 요청의 시간 조각이 아니어서 합산할 수 없다. `http_req_waiting`은 서버 코드 실행 시간만 뜻하지 않는다. 같은 PC에서 부하가 낮은 빈 DB의 API를 초당 10건으로 호출한 별도 연결 기준 시험에서는 전체 반복 p95 92ms, TCP 연결 p95 31ms, TLS p95 12ms였다. 다만 이 기준 시험은 데이터와 부하가 달라 HOT 계산 성능 비교로 사용하지 않는다. 연결 거절이 PC의 Docker 네트워크, 중간 경로, EC2의 수신 단계 중 어디서 생성됐는지는 동시 패킷 기록이 없어 확정하지 못했다.

부하 생성기만 따로 점검하기 위해 동일한 10,000건/초·1초·5,000 VU 설정에서 네트워크 호출을 제거했다. 이 경우 정확히 10,000번 실행됐다. 따라서 단순 예약 기능은 목표를 수행했지만, 실제 HTTPS 연결을 포함한 PC·Docker 네트워크·원격 접속 경로에서는 달성하지 못했다. 어느 구간에서 연결 거절을 보냈는지는 이번 자료만으로 확정할 수 없다. 시험 후 웹·앱·DB 컨테이너는 재시작 또는 OOM 없이 실행 중이었고, 443 포트와 HOT API는 정상 응답했다. 이 결과는 배포 서버가 1만 동시 요청을 처리할 수 있다는 증거도, 서버만이 실패 원인이라는 증거도 아니다.

참고로 1,000개 조건에서 1,000건/초·5초·1,000 VU의 출력 최소화 실행은 4,916건 모두 HTTP 200이었고 84번의 `dropped_iterations`가 발생했다. 성공 HTTP p95는 526ms였다. 앞선 원시 JSON 대량 출력 시험은 k6의 음수 HTTP 시간 등 비정상 시간값을 보여 성능 비교에서 제외했다. 원시 요약, 재현 스크립트, 96개 조건 오류 기록은 `artifacts/hot-k6-benchmark/`에 있다. 시험 데이터 제거 후 DB는 이벤트 0건·티켓 0건·사용자 1건·주문 0건이며, 자동 ID 시작값 617·164를 확인했다. 공개 HOT API도 HTTP 200과 빈 이벤트 목록을 반환했다.

## 500~1,000건/초와 1만 건/10~20초: 로컬·배포 동일 부하 비교 — 2026-09-25

앞 절의 1만 건/1초 대신 네 부하 패턴을 **로컬과 배포 서버에 같은 k6 v2.3.0 스크립트**로 적용했다. 두 앱에는 배포 컨테이너에서 복사한 **동일한 JAR**(SHA-256 `1E4850D64365696C247EEF31774D325ABB7DD39273C59A92B44A91FC7F1AFAB0`)를 사용했다. 로컬은 Windows Docker 네트워크의 Spring Boot HTTP 서버와 벤치마크 전용 MySQL 스키마에 직접 접속했다. 배포는 같은 PC의 k6에서 인터넷 HTTPS → EC2 Caddy → Spring Boot → MySQL로 접속했다. 따라서 앱 빌드는 같지만 전송 경로·TLS·호스트 사양은 다르다. 배포 EC2는 `m7i-flex.large`(2 vCPU, 8GiB)이다.

이벤트·티켓은 로컬 전용 스키마의 96/163, 500/859, 1,000/1,721건을 사용했다. 배포 DB에 원래 있던 96/163건과 주문 1건은 보존하고, 500·1,000건 조건에는 부족한 이벤트·티켓만 추가했다. 기존 96개 이벤트의 ID·이름·시작·종료 날짜 해시는 로컬과 일치한다. 배포 DB에는 주문으로 인한 티켓 판매량 **1건 차이**가 있어 판매량 합계는 로컬 10,945, 배포 10,946이다. 이 영향으로 1,000개 조건의 HOT 상위 7개 ID 집합은 같지만 순서 일부가 다르다. 성능 비교가 완전히 동일한 응답 본문 조건은 아니라는 점을 남긴다.

각 실행 직전 HOT 키를 한 번 조회해 5초 앱 캐시를 채웠다. 긴 실행에서는 캐시가 만료·갱신된다. 아래 기본 시험은 k6 기본값대로 VU별 TCP 연결을 재사용하며, 실행마다 새 k6 컨테이너를 시작했다. `constant-arrival-rate`로 500건/초 × 1초, 1,000건/초 × 1초, 1,000건/초 × 10초, 500건/초 × 20초를 예약했다. `전체 p95`는 k6 반복의 시작부터 응답/실패까지이며 연결·TLS 시간이 들어간다. `성공/실행`은 HTTP 200 수/실행 요청 수다. 각 데이터·패턴 조합은 한 번씩 수행했다.

| 이벤트 수 | 부하 | 로컬 성공/실행 | 로컬 전체 p95 | 배포 성공/실행 | 배포 전체 p95 |
|---:|---|---:|---:|---:|---:|
| 96 | 500건/1초 | 501/501 | 86.2ms | 502/502 | 100.7ms |
| 96 | 1,000건/1초 | 1,000/1,000 | 14.9ms | 1,004/1,004 | 712.7ms |
| 96 | 1만 건/10초 | 10,001/10,001 | 1.9ms | 10,000/10,000 | 93.3ms |
| 96 | 1만 건/20초 | 10,001/10,001 | 0.7ms | 10,001/10,001 | 19.8ms |
| 500 | 500건/1초 | 501/501 | 74.7ms | 500/500 | 70.7ms |
| 500 | 1,000건/1초 | 1,000/1,000 | 19.2ms | 995/995 | 864.4ms |
| 500 | 1만 건/10초 | 10,001/10,001 | 2.7ms | 10,001/10,001 | 128.6ms |
| 500 | 1만 건/20초 | 10,001/10,001 | 0.7ms | 10,001/10,001 | 23.0ms |
| 1,000 | 500건/1초 | 500/500 | 86.2ms | 501/501 | 92.3ms |
| 1,000 | 1,000건/1초 | 1,002/1,002 | 34.8ms | 1,010/1,010 | 565.9ms |
| 1,000 | 1만 건/10초 | 10,001/10,001 | 2.6ms | 10,001/10,001 | 200.6ms |
| 1,000 | 1만 건/20초 | 10,001/10,001 | 0.9ms | 10,000/10,000 | 22.0ms |

모든 기본 실행에서 k6의 `dropped_iterations`는 0이고 **실행된 요청은 모두 HTTP 200**이었다. 단, 500개 데이터의 배포 1,000건/1초 실행은 목표보다 5건 적은 **995건만 실행**했다. 다른 실행의 1~10건 초과는 k6 스케줄 경계에서 발생했다. 이 수치는 k6가 실행한 HTTP 요청 수이며 실제 서버에 도착한 패킷의 1초 구간을 별도로 검증한 값은 아니다. 연결 재사용 조건에서 배포 **500건/1초와 1만 건/10~20초의 전체 p95는 300ms 이내**였으나, **1,000건/1초는 세 데이터 규모 모두 300ms를 초과**했다. 이벤트 수가 작을수록 항상 빨라지지는 않아, 짧은 급증의 지연을 HOT 집계 데이터 크기만으로 설명할 수 없다.

### 새로 접속한 사용자와 연결 재사용의 차이

기본 k6 실행의 1만 HTTP 요청은 1만 명의 첫 접속과 같지 않다. 1,000개 데이터에서 **요청마다 새 TCP 연결**을 만드는 옵션으로 별도 비교했다.

| 부하·연결 조건 | 로컬 성공/실행·전체 p95 | 배포 성공/실행·전체 p95 |
|---|---:|---:|
| 1만 건/10초, 재사용 | 10,001/10,001 · 2.6ms | 10,001/10,001 · 200.6ms |
| 1만 건/10초, 매번 새 연결 | 10,000/10,000 · 1.0ms | **9,998/10,003 · 568.5ms** |
| 1만 건/20초, 재사용 | 10,001/10,001 · 0.9ms | 10,000/10,000 · 22.0ms |
| 1만 건/20초, 매번 새 연결·단독 실행 | 10,000/10,000 · 1.0ms | 10,001/10,001 · 30.2ms |

배포의 새 연결 10초 실행에서는 접속 거절 1건과 시간 초과 4건이 발생했다. 바로 뒤따른 새 연결 20초 실행은 **4,440/10,000건 성공, 5,560건 실패**(접속 거절 5,557건, 시간 초과 3건)했다. 이를 원시 자료에 `*-fresh-sequential.*`로 보존했다. 약 2분 후 20초 실행만 다시 하자 **10,001건 모두 성공**했다. 연속 시험의 연결 상태에 민감하다는 사실은 확인했지만, 거절이 부하 생성 PC·중간 경로·EC2 어디서 만들어졌는지는 그 실패 실행의 양쪽 패킷 기록이 없어 확정하지 않는다. 성공한 단독 20초 시험에서는 EC2에서 TCP SYN 약 10,003개와 SYN-ACK 약 10,003개를 관측했다. 이 실험으로 재사용 연결에서의 좋은 수치를 새 이용자 1만 명의 응답 시간으로 일반화하면 안 된다는 점이 드러났다.

### 병목 판단

배포 1,000개·1,000건/1초 기본 실행의 전체 p95는 **565.9ms**, TCP 연결 p95는 **143.3ms**, 첫 응답 바이트 대기 p95는 **169.4ms**, HTTP 요청 시간 p95는 **208.1ms**였다. 이 값들은 각각의 분포에서 계산한 p95이므로 합산할 수 없다. 같은 HOT 실행을 두 번 더 반복한 전체 p95는 **432ms, 418ms**였고 마지막 반복에서 접속 거절 1건이 있었다. 같은 Caddy를 통과하되 DB에는 닿지 않는 백엔드 경로(`/api/events/not-a-number`, 예상 HTTP 403)의 세 실행은 전체 p95가 **1,041ms, 479ms, 756ms**였다. Caddy가 직접 제공하는 정적 홈페이지의 1,000건/1초 단발 시험은 전체 p95 **147ms**였다. DB 비사용 경로도 느리고 정적 응답은 상대적으로 빠른 점은 **HOT SQL보다 연결·프록시·백엔드 공통 경로**의 순간 부하가 핵심임을 지지한다. 각 경로는 응답 본문과 상태가 달라 p95 차이를 특정 구성요소의 처리 시간으로 단정하지 않는다.

배포 1,000개 시험에서 약 2초 간격으로 본 컨테이너 CPU 최대 표본은 웹 프록시 약 **114%**(1코어=100%), 앱 약 **37%**, MySQL 약 **5%**였다. 1초 급증의 최고 순간은 이 간격으로 놓칠 수 있다. 앱 캐시가 있는 조건에서 이벤트 96→1,000개가 지연을 일관되게 키우지 않았고, DB 비사용 경로도 지연됐으므로 추가 SQL 인덱스를 이 병목의 첫 해결책으로 볼 근거는 없다. 그러나 PC의 Docker 네트워크, 인터넷, EC2 수신, Caddy→Tomcat 사이에서 정확히 어느 한 지점이 가장 큰지는 이번 기록으로 분리할 수 없다.

원시 k6 요약·오류 로그·재현 스크립트·집계 CSV는 `artifacts/hot-rps-comparison/`에 있다. k6 단계별 시간 정의는 [Grafana 공식 지표 설명](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)을 따른다. 시험 후 배포 DB의 **추가 행 904개 이벤트·1,558개 티켓만 제거**했고 원래의 이벤트 96건·티켓 163건·사용자 1건·주문 1건과 판매량 합계 10,946을 확인했다. 이벤트·티켓 자동 ID 시작값은 617·164다. 로컬 원본 `free_ticket`은 96/163건, 별도 `hot_bench_1000`은 1,000/1,721건을 유지하며 로컬 DB는 정상 종료해 시험 전의 정지 상태로 돌렸다.
