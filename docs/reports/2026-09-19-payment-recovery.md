# 결제 중 재고 보호와 커밋 실패 복구

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

2026-09-20에 미완료 결제 스케줄러를 추가했다. 아래는 요청 중 즉시 복구의 설명이며, 후속 복구 흐름·설정·수동 확인 기준은 [스케줄러 문서](2026-09-20-payment-recovery-scheduler.md)를 함께 참고한다.

## 해결한 문제

### 1. 결제 승인 중 주문 만료

결제 승인 요청 전에 첫 번째 트랜잭션에서 주문을 `CONFIRMING`으로 변경하고 커밋한다. 토스 승인과 최종 결제 반영은 이 트랜잭션 밖에서 진행한다.

재고 계산 쿼리는 `CONFIRMING` 주문을 만료 시각과 관계없이 예약 수량으로 계산한다. 따라서 토스 승인을 기다리는 동안 10분이 지나도 다른 주문이 같은 재고를 사용할 수 없다.

### 2. 토스 승인 후 DB 반영 또는 커밋 실패

토스 응답을 받은 뒤 실행하는 결제 완료 트랜잭션 B 전체를 `try/catch`로 감싼다. `TransactionTemplate.execute()`는 커밋까지 끝난 후 반환하므로 본문과 커밋 단계의 `RuntimeException`을 모두 처리한다. `ApiException`도 포함된다. 트랜잭션 A와 토스 승인 요청 자체의 실패는 이 복구 범위에 포함되지 않는다.

예외가 발생하면 실패한 트랜잭션을 끝낸 뒤 `recoverPayment()`가 새 트랜잭션에서 주문을 잠그고 DB 상태를 다시 확인한다. `completePayment()` 내부의 무조건 취소 catch는 삭제했다. 아래 분기는 최초 예외의 종류만 보고 판단하지 않고, 다시 조회한 DB 상태를 기준으로 결정한다.

| DB 상태 | 처리 |
| --- | --- |
| `PAID` + 해당 주문의 Payment 존재 + 요청의 결제 키·금액과 Payment 일치 + 주문 금액도 일치 + Payment 상태 `DONE` | 기존 결제 결과 반환 |
| `CONFIRMING` + 해당 주문의 Payment 없음 + 승인 응답 일치 + 재고 있음 | 로컬 결제 완료를 한 번 재시도 |
| 위 조건에서 티켓이 없거나 유효한 재고 수치상 수량 부족 | `CANCELING` 커밋 → 토스 취소 → 취소 응답 검증 → 별도 트랜잭션에서 `CANCELED` 커밋 |
| `PAID`의 결제 키·금액 불일치 또는 Payment 없음, `CONFIRMING`인데 Payment 존재, 그 밖의 주문 상태 | `PAYMENT_RECOVERY_PENDING` 반환 |
| 복구 DB 조회 실패, 재시도 본문·커밋 실패, 승인 응답 불일치, 재고 데이터 이상 | 취소하지 않고 `PAYMENT_RECOVERY_PENDING` 반환 |
| 취소 의도 커밋 실패 | 외부 취소를 호출하지 않고 `PAYMENT_RECOVERY_PENDING` 반환 |
| 취소 요청 실패·응답 불일치 또는 취소 후 DB 반영 실패 | 완료 재시도를 하지 않고 `PAYMENT_RECOVERY_PENDING` 반환 |

토스 승인 API는 한 번만 호출한다. 재시도에서는 이미 받은 `DONE` 응답을 사용해 주문, 결제 기록, 판매 수량만 다시 반영한다.

승인 응답은 결제 키·주문번호·금액·`DONE` 상태를 검증한다. 재고 필드의 null·음수·판매 수량 초과 등 데이터 이상은 정상적인 재고 부족으로 단정하지 않는다. 주문 조회 결과가 없을 때도 안전하게 잠글 주문이 없으므로 자동 취소하지 않는다.

정상 경로는 기존처럼 트랜잭션 A → 토스 승인 → 트랜잭션 B다. **실패 경로에는 DB 재확인·재시도 또는 취소 의도 저장용 트랜잭션이 추가된다.** 취소를 수행했다면 취소 결과를 저장하는 트랜잭션도 추가된다. 전체 흐름이 항상 트랜잭션 두 개만 사용하는 것은 아니다.

### 취소와 완료의 충돌 방지

`CANCELING`은 외부 취소를 진행하기로 결정한 상태다. 주문 잠금 안에서 `CONFIRMING` → `CANCELING`을 커밋한 다음 잠금을 해제하고 토스 취소를 요청한다. 이후 같은 주문으로 들어오는 승인 요청은 상태 검증에서 거절되고, 복구도 `CONFIRMING`에서만 완료를 시도한다.

`OrderService.createOrder`의 조회 상태 목록과 `OrderRepository.sumActiveQuantity`에 `CANCELING`을 포함했다. `CONFIRMING`과 `CANCELING`은 만료 시각이 지나도 예약 수량으로 계산한다. 취소 결과가 불명확한 동안에는 재고를 풀지 않는다.

취소 멱등성 키는 승인 키와 구분한 `cancel:{주문의 idempotencyKey}`다. 토스 응답의 결제 키·주문번호·금액·`CANCELED`가 일치해야 DB를 `CANCELED`로 바꾼다. 마지막 DB 트랜잭션에서도 주문을 잠그고 결제 정보 일치·Payment 부재·상태 전이 가능 여부를 확인한다. 요청 중 취소와 DB 반영이 모두 성공하면 `409 PAYMENT_CANCELED`를 반환한다. 스케줄러의 취소 상태 조회에서는 `CONFIRMING`에 남은 주문도 동일한 검증 후 취소 상태로 정리할 수 있다.

## 변경된 코드

- `PaymentService.confirm`: 두 번째 트랜잭션의 본문·커밋 예외를 외부에서 처리한다.
- `PaymentService.recoverPayment`: 성공 반환·한 번 재시도·확정 취소·판단 보류를 결정한다. 재시도 실패를 다시 이 메서드로 넘기지 않으므로 반복 복구하지 않는다.
- `PaymentService.completePayment`: 주문 상태와 승인 응답, 재고를 검증하며 예외를 호출자에게 전달한다.
- `PaymentService.applyPayment`: 이미 검증하고 잠근 주문·티켓에 판매 수량 증가, PAID 변경, Payment 저장을 함께 적용한다. 최초 완료와 복구 재시도에서 공통으로 사용한다.
- `PaymentService.validateApproval` / `canFulfill`: 승인 응답 일치 여부와 티켓 제공 가능 여부를 확인한다.
- `PaymentService.recoveryPending`: 자동으로 결론을 내릴 수 없는 경우 재결제하지 말고 주문번호로 문의하라는 안내와 `503 PAYMENT_RECOVERY_PENDING` 응답을 만든다. 이 응답 자체가 후속 복구를 예약하지는 않는다.
- `PaymentCommitFailureIntegrationTest`: 토스 호출 위치가 아니라 첫 `Payment` 저장 트랜잭션의 `beforeCommit`에서 예외를 발생시킨다. 변경 전후에 같은 테스트를 사용한다.

## 동일 테스트의 RED/GREEN 결과

문제 1까지만 적용된 코드에서 결과:

```text
Toss: DONE
첫 결제 커밋: ROLLED_BACK
서비스 결과: INJECTED_BEFORE_COMMIT_FAILURE
DB: order=CONFIRMING, payments=0, sold=0
테스트: FAIL
```

문제 2 적용 후 같은 테스트의 결과:

```text
Toss: DONE
첫 결제 커밋: ROLLED_BACK
서비스 결과: DONE
DB: order=PAID, payments=1, sold=1
Toss 승인 호출: 1회
테스트: PASS
```

최초 최소 복구 구현 당시 전체 테스트는 47개가 통과했다. 2026-09-20에는 `PaymentServiceTest`에 결제 키·결제 금액·주문 금액 불일치 3건, 정상 결제 반환 1건, `CONFIRMING`에 Payment가 이미 있는 경우 1건을 추가했다. 수정 전 누락된 조건에 해당하는 4건의 실패를 확인하고, 복구 분기의 조건만 보강했다.

키·금액 검증 보강 당시 전체 테스트는 52개 실행, 실패 0개, 오류 0개, 건너뜀 0개였다. 기존 `PaymentExpiryIntegrationTest`와 `PaymentCommitFailureIntegrationTest`도 수정 없이 통과했다. 추가한 단위 테스트는 커밋 예외 이후 조회 상태를 대체해 분기를 검증하며, 실제 DB 롤백과 재시도는 기존 H2 통합 테스트가 검증한다.

## 이번 추가 테스트

`PaymentRecoveryIntegrationTest`는 실제 Spring 트랜잭션·H2 DB를 사용하고 토스 호출만 대체한다. Repository spy는 장애를 주입할 때 사용한다. 기존 문제 1·2 통합 테스트의 시나리오와 기대 결과는 이번 작업에서 변경하지 않았다.

- 저장 본문의 일시적 RuntimeException / ApiException → 한 번 재시도로 PAID, Payment 1건, 판매 수량 1, 취소 0회.
- 지속적인 저장 장애 / 복구 조회 장애 / 승인 정보 불일치 → 확인 필요 응답, 자동 취소 없음.
- 확정 재고 부족 → 외부 취소 전에 CANCELING이 실제로 커밋되고, 외부 호출 중 DB 트랜잭션이 열려 있지 않음.
- 취소 진행 중 만료와 중복 승인 → 예약 수량 유지, 중복 승인 차단.
- 취소 응답 유실·불일치 / CANCELING 커밋 실패 / CANCELED 커밋 실패 → 무조건 재고를 풀거나 완료를 다시 시도하지 않음.
- 실제 커밋 후 `afterCommit` 콜백 예외 → 저장된 PAID 반환, 중복 저장·취소 없음. 네트워크상의 DB 커밋 응답 유실 자체를 재현한 테스트는 아니다.

새 테스트 최초 실행은 14개 중 13개 실패했다. 실제 커밋 후 저장된 성공을 반환하는 1개는 기존 코드에서도 통과했다.

구현 후 14개가 모두 통과했고, 취소 중 실제 주문 생성 차단·취소 후 재고 해제 검증을 강화하고 티켓 데이터 이상·티켓 삭제 2개를 추가했다. 2026-09-20 최종 `./gradlew.bat test --no-daemon` 결과는 전체 **68개 실행, 실패 0개, 오류 0개, 건너뜀 0개**다. 새 복구 통합 테스트는 16개이며 기존 문제 1·2 통합 테스트도 그대로 통과했다.

## 현재 범위와 미확정 주문 처리

요청 중 즉시 복구는 토스 승인 응답을 받은 뒤 DB 완료 처리에서 예외가 발생한 경우를 처리한다. 이후 추가한 스케줄러는 승인 응답 유실이나 서버 중단으로 남은 CONFIRMING·CANCELING도 토스 상태 조회를 통해 다시 확인한다.

`PAYMENT_RECOVERY_PENDING` 이후에는 DB에 남은 복구 예약을 스케줄러가 확인한다. 한도 초과 또는 복구 정보 누락·DB 상태 불일치로 수동 확인 표시가 남으면 운영자가 DB 주문·Payment·판매 수량과 토스 결제 상태를 대조해야 한다. `CONFIRMING` / `CANCELING`을 만료만 보고 `PENDING` 또는 종료 상태로 바꾸면 안 된다. 수동 처리용 API나 관리 화면은 아직 없다.

현재는 트랜잭션 A에서 결제 키와 다음 확인 시각을 DB에 저장한다. 따라서 Payment 저장 전 서버가 종료되어도 토스 조회로 복구할 수 있다. 예전 데이터에 결제 키가 없으면 수동 확인이 필요하다. 예약 수량을 안전하게 유지하는 대신 장기 미해결 주문이 재고를 계속 점유할 수 있다는 제한은 유지된다.

스케줄러 추가와 함께 이미 `PAID`인 주문의 초기 반환 경로에도 요청 결제 키·금액과 Payment 상태 검증을 적용했다. MySQL 배포 시 신규 복구 컬럼과 `CANCELING` 허용 여부를 확인해야 한다. 성능용 인덱스 선언은 2026-09-21에 제거했다. 이번 검증은 H2 기준이며 실제 DB 인덱스 삭제 여부는 스케줄러 문서를 참고한다.
