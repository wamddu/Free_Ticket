# 예매 내역 조회의 N+1 제거

> 2026-09-15 작업 기록을 정리한 문서다. 수치는 당시 테스트 결과이며, 응답 시간은 측정하지 않았다.

## 요약

`GET /api/orders/me/reservations`는 예매 건마다 티켓을 다시 조회하고, 결제 기록이 없는 `PAID` 주문을 찾는 보완 조회까지 하고 있었다. 보완 조회는 정상 결제 경로에서 필요하지 않아 제거했다. 티켓 조회는 `IN` 일괄 조회로 바꿨다. 서비스 조회는 **결제·주문 목록 1회 + 티켓·공연 최대 1회**가 됐다.

## SQL을 API별로 구분하기

API를 하나씩 호출하며 SQL을 관찰했지만, 출력된 SQL만으로는 어느 API에서 실행됐는지 알기 어려웠다. 요청 필터와 MDC로 요청 ID를 붙이는 방법도 검토했다. 다만 한 번에 한 API만 호출해 확인할 계획이었으므로, 서비스 메서드에 시작·종료 DEBUG 로그를 넣는 단순한 방법을 택했다.

```text
[SQL CHECK] GET /api/orders/me/reservations START
Hibernate: select ...
[SQL CHECK] GET /api/orders/me/reservations END
```

이 로그는 분석용 임시 장치였고, 2026-11에 모두 제거했다.

## 원인

공연 목록, HOT, 주간 순위, 공연 상세는 DTO 직접 조회나 DB 집계로 응답을 만들었다. 건수에 비례하는 추가 조회가 없었다. 문제는 예매 내역이었다.

```java
for (Payment payment : payments) {
    Ticket ticket = ticketRepository.findByIdWithEvent(payment.getOrder().getTicket_id()).orElse(null);
    // 응답 생성
}
```

티켓 조회에 fetch join이 있어도 티켓 하나와 공연 하나를 함께 가져올 뿐이다. 이 호출을 예매마다 반복하므로, 예매 수만큼 조회가 늘었다. 지연 로딩 때문이 아니라 **반복문 안에서 명시적으로 조회한 N+1**이었다.

## 최적화 전에 불필요한 조회부터 제거

당시 코드는 결제 내역으로 응답을 만든 뒤, `PAID` 주문을 다시 조회해 빠진 주문을 보완했다. 그런데 `PaymentService.confirm()`은 같은 트랜잭션에서 주문을 `PAID`로 바꾸고 결제 기록을 저장한다. 정상 결제 경로에서는 보완할 주문이 생기지 않으므로 두 번째 조회와 중복 방지용 `processedOrderIds`를 제거했다.

과거 데이터나 수동 입력까지 포함해 "PAID에는 항상 결제 기록이 있다"를 증명한 것은 아니다.

## 일괄 조회로 변경

1. 결제와 주문을 fetch join으로 한 번에 조회한다.
2. 주문의 티켓 ID에서 null과 중복을 제거한다.
3. `IN` 쿼리로 티켓과 공연을 한 번에 조회한다.
4. 티켓 ID를 키로 `Map`에 담고, 반복문에서는 DB 대신 Map에서 찾는다.

```java
@Query("SELECT T FROM Ticket T LEFT JOIN FETCH T.event WHERE T.id IN :ids")
List<Ticket> findAllWithEventByIdIn(@Param("ids") List<Long> ids);
```

조회 횟수를 줄인 핵심은 `IN`이다. 반복문은 남아 있지만, 그 안의 DB 호출을 없앤 것이 중요하다. 조회할 ID가 없으면 티켓 쿼리를 생략한다.

| 단계 | 서비스 조회 구조 |
|---|---|
| 최초 | 결제·주문 목록 1회 + 티켓 N회 + PAID 주문 1회 + 보완 티켓 M회 |
| 보완 조회 제거 | 결제·주문 목록 1회 + 티켓 N회 |
| 일괄 조회 | 결제·주문 목록 1회 + 티켓·공연 **최대 1회** |

## 검증

- "예매가 여러 건이어도 티켓 Repository를 한 번만 호출한다"는 테스트를 먼저 작성했고, 기존 코드에서 실패하는 것을 확인했다.
- 변경 후 빈 목록, null 티켓 ID, 보완 조회를 하지 않는지(`verifyNoInteractions`)를 검증했다.
- 백엔드 전체 테스트 통과. 수동 호출에서 SQL 2회로 조회되는 것을 확인했다.

## 한계

- 호출 횟수 검증은 Mockito 단위 테스트다. 실제 DB의 SQL 횟수를 자동으로 세는 통합 테스트는 아니다.
- 응답 시간, p95, DB 부하는 측정하지 않았다. 조회 횟수가 일정해도 처리하는 행 수와 응답 크기는 예매 수에 따라 늘어난다.

## 함께 검토한 것

- **판매량 내림차순 인덱스로 HOT을 빠르게 할 수 있나:** HOT은 티켓별 판매량이 아니라 공연별 합계로 정렬한다. 예를 들어 공연 A의 티켓이 100·10장, B가 70·60장이면 티켓 순서는 A가 앞서지만 합계 순위는 B(130)가 앞선다. 그래서 `sold_ticket` 인덱스만으로는 순위를 얻을 수 없다. 이후 짧은 캐시와 쿼리 구조 개선을 택했다([HOT API 성능 측정](2026-09-24-hot-api-performance.md)).
- **인덱스 후보:** 코드에서 후보를 뽑았지만, 실행 계획을 확인하기 전에는 만들지 않았다. 이후 측정을 거쳐 `orders(ticket_id)`와 인증 관련 인덱스를 적용했다([주문 인덱스](2026-10-31-orders-ticket-index.md), [인증 인덱스](2026-10-31-auth-indexes.md)).
