# 인증 관련 인덱스 3개 전후 성능 비교

> 작성일 당시의 기록이다. 본문에 나오는 측정 스크립트·원시 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 코드 위치와 수치는 작성 시점 기준이다.

추가 대상: `users(phonenumber)`, `refresh_tokens(expires_at)`, `refresh_tokens(user_id)`. 모두 일반 비고유 인덱스이며 기존 데이터 제약과 업무 로직은 유지한다.

## 실험 조건

- 실제 로컬 DB와 AWS 대신 기존 격리 테스트 DB를 사용했다. 이전 주문 인덱스는 두 조건에 모두 유지했다.
- 동일 앱 이미지 `free-ticket-perf:7f451dd`에서 DB 인덱스 3개 유무만 변경했다. 수정된 Java 선언은 별도 사용자/인증 테스트 52건 통과.
- 앱·MySQL 각각 CPU 0.5개, 메모리 768MiB. 버퍼 풀 128MiB, 클라이언트 제한 30초. MySQL SELECT 제한 8초이며 DELETE·잠금 대기를 8초로 제한하는 설정은 아니다.
- 매 wave에 사용자 101,500명(배경 100,000명+요청자/관리자 fixture 1,500명), 토큰 105,000개(배경 100,000개+요청자 500명×10세션)를 준비했다. 만료 토큰은 배경의 1,000개다.
- 매 wave 전에 서버 재시작 → 같은 API 단일 요청 예열 → 전체 측정 fixture 재설정 순서를 지켰다. wave 후 서버를 중단하고 DB 요청 종료를 기다린 다음 저장 결과를 검사했다.
- 6개 API를 50/100/500명 각 1회 전후 비교했다. 전화번호 수정·로그인·회원탈퇴는 100명 wave를 전후 각 3회 반복했다. 총 48 wave / 9,000개 측정 요청. 예열·준비 요청 제외.
- 전체 before 블록 다음 after 블록 순서다. 이전 보고서보다 사용자·토큰이 많으므로 과거 수치와 직접 비교하지 않는다.
- 사용자마다 별도 계정·전화번호·인증 증명을 사용했다. 비밀번호는 실제 BCrypt cost 10을 유지했다. 외부 결제·SMTP·Gemini 호출은 없다.

## SQL 단위 근거

전화번호 조회는 실제 실행 행 수를 보여주는 EXPLAIN ANALYZE를 사용했다. 아래 값은 단일 진단 실행으로 API P95나 반복 평균과 다르다.

적용 전:
```text
-> Limit: 1 row(s)  (cost=12198 rows=1) (actual time=90.4..90.4 rows=0 loops=1)
    -> Filter: (users.phonenumber = '01800000001')  (cost=12198 rows=11280) (actual time=90.4..90.4 rows=0 loops=1)
        -> Table scan on users  (cost=12198 rows=112797) (actual time=0.0343..85.5 rows=101500 loops=1)
```

적용 후:
```text
-> Limit: 1 row(s)  (cost=1.1 rows=1) (actual time=0.608..0.608 rows=0 loops=1)
    -> Covering index lookup on users using idx_users_phonenumber (phonenumber='01800000001')  (cost=1.1 rows=1) (actual time=0.0215..0.0215 rows=0 loops=1)
```

토큰은 실제 DELETE SQL을 각각 3회 실행하고 매번 ROLLBACK했다. 대상은 만료 1,000개, 사용자별 10개이며 전후 삭제 건수와 경계 조건이 같다. 아래 시간은 서버 내부 NOW(6) 차이이며 클라이언트 실행 시간이 아니다.

| DELETE 조건 | 전 중앙값(ms) | 후 중앙값(ms) | 전후 삭제 건수 |
|---|---:|---:|---:|
| expires_at <= 기준시각 | 48.563 | 6.543 | 1000 |
| user_id = 대상 사용자 | 41.190 | 0.584 | 10 |

실제 DELETE의 EXPLAIN FORMAT=JSON은 results/*-expiry-explain.json 및 *-revoke-explain.json에 보관했다. 실행 계획의 rows_examined_per_scan은 추정치다.

## 해석

- 전화번호 수정은 비밀번호 해시 작업을 거치지 않고 전화번호 조회 인덱스의 영향을 보기 쉽다. 회원가입은 BCrypt와 인증 증명 처리도 포함한다.
- 로그인은 매 wave 시작 시 1,000개의 만료 토큰이 있는 일괄 정리 상황이다. 첫 성공 로그인 이후에는 이 만료 목록이 소진되므로 모든 로그인 요청이 1,000개씩 삭제하는 시험은 아니다.
- 비밀번호 변경·재설정·회원탈퇴는 사용자별 10개 토큰 삭제를 포함한다. BCrypt CPU 비용과 DELETE의 잠금·스캔 비용이 전체 지연에 함께 반영된다.
- 시간 초과된 요청이 이후 커밋했을 수 있어 성공 응답 수와 최종 변경 행 수가 항상 같지는 않다. 확인된 성공 요청의 변경과 토큰 취소는 DB에서 검증했다.
- 성공한 로그인이 있는 wave에서 새 대상 토큰 수가 성공 수 이상 늘었는지도 보관된 token_counts_after로 검증했다.
- deadlock_log_mentions는 로그 문자열 출현 수다. 중복 예외 로그를 포함할 수 있으므로 고유 데드락/실패 트랜잭션 건수로 해석하지 않는다.
- 3개 인덱스를 한 번에 적용한 비교다. SQL·호출 경로로 직접 관련성을 확인했지만 각 인덱스의 시스템 전체 기여율을 분리 측정한 것은 아니다.
- 50/500명은 1회씩, 핵심 100명은 3회다. 실행 순서·공유 호스트·캐시·JVM 예열 영향이 남으므로 운영 개선율이나 장시간 처리량을 보장하지 않는다.

## 변경과 검증

- User.java 및 RefreshToken.java 인덱스 선언, backup.sql 신규 스키마, db/2026-10-31-auth-indexes.sql 기존 DB용 SQL에 반영.
- 실제 MySQL 8에서 SQL 적용 및 실행 계획 확인. 시각이 기준과 같은 만료 토큰은 삭제되고 1초 미래 토큰은 유지됨을 트랜잭션/롤백으로 전후 검증.
- 성공한 전화번호 수정의 값·계정 상태, 회원가입 인증 완료/증명 소비, 비밀번호 변경 및 토큰 취소, 배경 사용자 토큰 보존을 검사했다.
- 기존 사용자·인증 테스트 52건 통과. 테스트 컨테이너는 측정 후 정지했다.
- 운영 DB는 ddl-auto=validate이므로 배포 시 migration SQL을 해당 DB에 한 번 적용해야 한다. 일반 전화번호 인덱스는 중복 저장을 막는 UNIQUE 제약을 추가하지 않는다.

## 최종 판단과 남은 오류

- 전화번호 수정은 100명 반복에서 P95 중앙값 5.561초 → 2.403초(-56.8%), 500명 첫 회차 26.895초 → 11.269초(-58.1%)로 개선됐다. 모든 요청이 성공했고 반복 범위도 겹치지 않아 효과가 뚜렷하다.
- 만료 삭제 SQL 중앙값은 48.563ms → 6.543ms(-86.5%), 사용자별 취소 SQL은 41.190ms → 0.584ms(-98.6%)로 줄었다. 인덱스가 사용되는 실행 계획도 확인했다.
- 로그인 100명 3회는 성공 225/300(75.0%) → 287/300(95.7%), P95 중앙값 17.483초 → 16.463초다. 적용 후에도 13건의 HTTP 403이 남았다. 로그에서 만료 DELETE와 토큰 INSERT의 데드락을 확인했다. 인덱스만으로 동시 로그인 문제가 해결되지는 않았다.
- 회원탈퇴 100명 반복 P95 중앙값은 16.064초 → 15.521초(-3.4%)다. 전후 지연 범위가 겹쳐 API 차원의 큰 개선을 주장하기 어렵다.
- 적용 후 비밀번호 변경 500명은 74건 성공, 425건 시간 초과, 1건 HTTP 403이다. 해당 로그는 Hikari 풀 10개가 모두 사용 중이고 117개가 대기하다 30,095ms 후 연결 획득에 실패했음을 보여준다. 이 403은 자격 증명 오류로 해석하지 않는다.
- 위 wave의 docker stats 9개 표본에서 앱 CPU 중앙값 48.26%, DB CPU 3.29%였다. 앱 한도가 0.5 CPU인 점을 고려하면 앱 CPU가 병목이라는 추론을 지지한다. BCrypt 자체의 CPU 비중은 프로파일링하지 않았다.
- 다음 개선 실험은 로그인에서 전역 만료 삭제를 분리하는 방안과 인증 트랜잭션의 커넥션 점유 시간이다. 기존 비밀번호/로그인 경합 방지 규칙을 보존하며 검증해야 한다.
