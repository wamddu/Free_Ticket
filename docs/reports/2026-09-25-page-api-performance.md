# 화면 단위 API 성능 측정 — 2026-09-25

> 작성일 당시의 측정 기록이다. 재현 스크립트와 k6 결과 파일은 용량 때문에 저장소에 포함하지 않았다. 이 보고서의 '다음 작업' 1·2번(주간 순위 중복 계산 제거와 캐시, 이벤트 목록 페이지 나누기)은 이후 반영했고, 같은 시나리오의 재측정 결과는 [2026-11-14 재측정](2026-11-14-page-api-remeasure.md)에 있다.

## 결론

**HOT 한 건의 속도만으로 화면 성능을 예측할 수 없다.** 메인 화면은 HOT 조회 한 건이지만, 장르 화면은 이벤트 목록·HOT·주간 순위를 동시에 요청한다. 익명 방문자의 새 브라우저 세션에서는 인증 갱신 요청도 병렬로 한 건 발생한다. 1,000개 이벤트 조건에서 배포 서버에 화면 방문 500건/초를 보냈을 때, 메인만 따로 요청하면 화면 API 완료 p95가 **417ms**였고 콘서트 화면만 따로 요청하면 **3,634ms**였다. 같은 부하의 API 단독 시험에서 HOT p95 **70ms**, DB를 쓰지 않는 백엔드 경로 **72ms**, 이벤트 목록 **668ms**, 주간 순위 **461ms**였다. 장르 화면의 목록·주간 순위와 요청 수 증가가 현재의 우선 병목이다.

배포 서버에서 1,000개 이벤트·브라우저 gzip 조건의 혼합 화면 방문은 **500건/초 급증에서 486/502건 성공**, **1,000건/초 급증에서 985/999건 성공**했다. 후자의 장르 화면 p95는 **5.16~5.40초**였다. 1만 방문을 10초 또는 20초에 나눈 시험도 실패와 부하 생성기 미시작이 발생했다. 따라서 이 구성에서 **300ms 이내 화면 완료**나 **1만 명/10~20초 처리**가 달성됐다고 볼 수 없다.

## 실제 화면 호출과 측정 범위

| 화면 | 익명 새 세션에서 발생하는 API | 완료 시간 기준 |
|---|---|---|
| 메인 `/` | `POST /api/auth/refresh`(쿠키 없으면 예상 401)와 `GET /api/events/whats-hot?limit=7` 병렬 | 두 응답 완료 |
| 콘서트·뮤지컬·연극·클래식·전시·버스킹 | 인증 갱신과 `GET /api/events?category=...`, `GET /api/events/whats-hot?category=...&limit=5`, `GET /api/events/weekly-ranking?category=...&limit=5` 병렬 | 네 응답 완료 |
| 티켓 상세 `/ticket/107` | 인증 갱신과 `GET /api/events/107` 병렬, 상세 결과에서 선택된 티켓의 `GET /api/events/107/tickets/96/price-history` 후속 호출 | 세 응답 완료 |

코드를 확인해 메인 화면의 비즈니스 API는 **HOT 한 건**임을 확인했다. 테스트는 메인·장르 6개·티켓 상세를 각각 12.5%로 섞었다. 따라서 화면 방문 500건/초는 평균 약 **1,813개 HTTP 요청/초**, 1,000건/초는 약 **3,625개 HTTP 요청/초**다. 이는 기존 HOT 단일 API의 500~1,000건/초 시험보다 훨씬 큰 백엔드 부하다.

실제 브라우저 렌더링, 정적 파일, 외부 이미지·지도 로딩, 로그인·주문·결제·마이페이지는 측정하지 않았다. 이벤트·티켓 더미 데이터만으로 재현할 수 있는 **익명 공개 화면의 API 완료 시간**이다. 인증 갱신의 401은 정상 결과로 취급했고, 각 화면의 모든 기대 응답을 받았을 때만 성공으로 계산했다.

## 환경과 방법

- 로컬 DB는 이벤트/티켓 **96/163, 500/859, 1,000/1,721**의 별도 스키마를 사용했다. 로컬 원본 `free_ticket`의 96/163행은 변경하지 않았다.
- 로컬 앱과 배포 앱은 같은 JAR(SHA-256 `1E4850D64365696C247EEF31774D325ABB7DD39273C59A92B44A91FC7F1AFAB0`)다. 로컬 k6 → Docker HTTP 앱 → MySQL과 PC k6 → 인터넷 HTTPS → EC2 Caddy → 같은 앱 → MySQL을 비교했다.
- k6 v2.3.0 `constant-arrival-rate`, HTTP 연결 재사용, 요청당 20초 타임아웃을 사용했다. 매 실행 전에 8개 화면 API를 한 번씩 호출했다. HOT 앱 캐시는 5초이며 긴 시험 중 만료된다.
- 브라우저에 가깝게 `Accept-Encoding: gzip`을 보낸 결과를 아래 급증 시험의 주 표로 삼았다. 배포 Caddy는 gzip을 사용하지만 로컬 직접 연결 앱은 gzip으로 응답하지 않으므로 전송 경로는 여전히 다르다.
- 배포 DB는 시작 시 이벤트·티켓·사용자·주문 모두 **0건**이었다. 측정용 행만 넣었고 종료 시 이벤트·티켓·사용자·주문 모두 **0건**을 재확인했다.
- 500→1,000개 전환 때 후보 추가 SQL의 티켓 ID가 현행 500개 세트와 384건 겹치는 것을 적재 전에 발견했다. 이 SQL은 실행하지 않았고, 연관 테이블 0건을 확인한 뒤 **이번 시험에서 넣은 행만 비우고** 이미 검증한 1,000개 전체 SQL로 다시 적재했다.
- 각 조합은 기본적으로 한 번 실행했다. 몇 조합은 재시험했고 편차를 아래에 명시했다. `시작`은 k6가 실제 시작한 화면 방문 수이며 목표 수와 다를 수 있다. `미시작`은 k6의 `dropped_iterations`다. p95는 **실패 방문도 포함**하므로 실패가 있는 행에서는 성공 사용자만의 지연이 아니다.

## 1초 급증: 화면별 결과

아래 p95는 화면의 API 묶음 완료까지 걸린 밀리초다. 장르 열은 여섯 장르의 p95 최솟값~최댓값이다. 모두 gzip 요청 조건이다. 500개 로컬은 앱 준비 완료 후 재시험 값, 500개 배포 500건/초는 연속 과부하 뒤 단독 재시험 값이다.

| 이벤트 | 방문/초 | 환경 | 성공/시작 | 메인 p95 | 장르 6개 p95 | 상세 p95 |
|---:|---:|---|---:|---:|---:|---:|
| 96 | 500 | 로컬 | 501/501 | 71ms | 72~96ms | 103ms |
| 96 | 500 | 배포 | 496/497 | 1,587ms | 1,479~1,589ms | 1,884ms |
| 500 | 500 | 로컬 | 501/501 | 1,327ms | 1,181~1,412ms | 1,475ms |
| 500 | 500 | 배포 | 481/490 | 1,903ms | 1,914~2,059ms | 2,262ms |
| 1,000 | 500 | 로컬 | 500/500 | 1,052ms | 1,062~1,147ms | 1,161ms |
| 1,000 | 500 | 배포 | 486/502 | 2,502ms | 2,455~2,590ms | 2,846ms |
| 96 | 1,000 | 로컬 | 1,000/1,000 | 2,066ms | 2,134~2,229ms | 2,336ms |
| 96 | 1,000 | 배포 | 985/985 | 3,211ms | 3,116~3,269ms | 3,427ms |
| 500 | 1,000 | 로컬 | 993/993 | 1,367ms | 1,469~1,716ms | 1,663ms |
| 500 | 1,000 | 배포 | 799/866 | 4,199ms | 4,134~4,280ms | 4,571ms |
| 1,000 | 1,000 | 로컬 | 1,001/1,001 | 1,904ms | 2,127~2,205ms | 2,319ms |
| 1,000 | 1,000 | 배포 | 985/999 | 5,278ms | 5,160~5,404ms | 5,784ms |

장르별 p95 차이는 같은 데이터 규모 안에서 작았다. 여섯 장르는 같은 페이지 컴포넌트와 SQL 구조를 사용하기 때문에 특정 장르 하나의 문제가 아니라 공통 조회 경로가 느려진다. 500개 배포·1,000건/초에서는 목표 1,000건 중 **866건만 시작**했으며 `dropped_iterations`는 0이었다. 이처럼 1초 스케줄 자체가 부하 생성기의 순간 처리량에 영향을 받았다.

## 1만 방문/10~20초: 성공 수

`성공/시작 (미시작)` 형식이다. `gzip`은 브라우저 압축 요청, `일반`은 기존 HOT 시험과 동일한 압축 없는 k6 요청이다. 장시간 시험은 모든 조합에서 하나의 압축 조건으로 완결하지 못했으므로, **서로 다른 압축 조건의 지연 숫자를 직접 비교하지 않는다**. 다만 각 행에서 실패가 발생했는지는 확인할 수 있다.

| 이벤트 | 환경 | 1만 방문/10초 | 1만 방문/20초 |
|---:|---|---:|---:|
| 96 | 로컬 | 일반 5,358/9,002 (2) | 일반 8,365/10,001 (0) |
| 96 | 배포 | 일반 1,634/9,997 (0) | gzip 6,074/9,135 (866) |
| 500 | 로컬 | 일반 6,368/9,998 (0) | 일반 8,347/10,001 (0) |
| 500 | 배포 | 일반 1,572/10,001 (0) | gzip 4,834/7,800 (2,200) |
| 1,000 | 로컬 | gzip 6,363/9,995 (0) | gzip 8,335/10,001 (0) |
| 1,000 | 배포 | gzip 2,430/7,289 (2,695) | gzip 4,202/6,784 (3,216) |

로컬 1,000개·20초의 **초기 일반 요청 실행은 10,000/10,000 성공**이었다. 그러나 후속 gzip 실행은 8,335/10,001, 앱을 새로 시작해 단독 반복한 실행은 **8,728/10,390**으로 둘 다 시간 초과가 났다. 이 시험의 로컬 안정 용량을 최초 성공 한 번으로 판정하면 안 된다. 1만 목표인데 시작이 10,390건으로 초과한 반복도 있어, 매우 높은 부하에서 생성기 스케줄 정확도에도 한계가 있다.

## 병목 근거

**동일 1,000개 데이터·배포·500방문/초의 분리 시험**을 했다. 메인과 콘서트 각각의 시험은 화면 방문 기준, 아래 API들은 한 종류의 HTTP 요청 500건/초 기준이다.

| 대상 | 성공/시작 | p95 |
|---|---:|---:|
| 메인 화면: HOT + 익명 인증 갱신 | 499/499 | 화면 417ms |
| 콘서트 화면: 목록 + HOT + 주간 순위 + 인증 갱신 | 501/501 | 화면 **3,634ms** |
| HOT 단독 | 500/500 | HTTP **70ms** |
| 이벤트 목록 단독 | 500/500 | HTTP **668ms** |
| 주간 순위 단독 | 501/501 | HTTP **461ms** |
| 상세 조회 단독 | 501/501 | HTTP 57ms |
| DB 비사용 백엔드 경로 단독 | 501/501 | HTTP 72ms |

단독 HTTP p95는 TCP 연결·TLS 시간을 제외하는 k6의 `http_req_duration`이다. 화면 p95와 산술 비교할 수는 없지만, **목록·주간 순위가 HOT·DB 비사용 경로보다 느리고, 네 요청을 함께 보내면 지연이 크게 늘어난다**는 순서는 분명하다. 콘서트 화면 단독 시험에서는 인증 갱신까지 포함한 네 API 모두 응답 대기 p95가 약 2.2~2.5초로 함께 늘었다. 특정 API 하나가 느린 동안 다른 요청도 공유 자원에서 대기한 것이다.

배포 MySQL의 누적 `performance_schema`에서 주간 순위 SQL은 **41,288회·총 371.41초·평균 9.00ms**, 이벤트 목록 SQL은 **41,164회·총 103.13초·평균 2.51ms**, HOT SQL은 **643회·총 4.25초·평균 6.61ms**였다. 여러 데이터 규모와 여러 실행을 합친 수치다. HOT의 5초 캐시로 DB 실행 횟수가 현저히 적은 반면, 주간 순위는 매 방문마다 집계한다. 1,000개·20초 배포 시험 중 약 2초 간격의 자원 표본 한 번에서 Caddy 약 60%, 앱 약 63%, MySQL 약 87% CPU(1코어=100%)가 관측됐다. EC2는 2 vCPU이므로 세 구성 요소가 동시에 CPU를 사용해 여유가 적은 상태였다. 이 표본만으로 CPU 원인을 하나로 확정하지는 않는다.

목록 API는 페이지 나누기 없이 해당 장르의 전체 이벤트를 내려준다. 콘서트 응답은 이벤트 96개 조건 **6,962B 일반/1,949B gzip**, 500개 조건 **38,381B/3,836B**, 1,000개 조건 **77,861B/5,965B**였다. 브라우저 전송은 gzip 덕분에 작아지지만, 서버는 여전히 전체 행을 읽고 JSON을 만든다. 주간 순위 SQL의 누적 DB 시간과 목록의 전체 조회·직렬화가 장르 화면에서 먼저 줄여야 할 비용이다.

연결 거절의 정확한 발생 위치는 확정하지 못했다. 배포 96개·500방문/초 반복의 짧은 EC2 패킷 기록 구간에서는 외부 SYN 1,729개에 SYN-ACK 1,729개가 관측됐고, 확인 시 Linux `ListenOverflows`·`ListenDrops`는 0이었다. k6에는 같은 실행에서 연결 거절 16건이 있었다. 기록 구간 밖의 연결이나 클라이언트 Docker/NAT·중간 경로까지 추적하지 않았으므로 이를 Caddy 수신 대기열 문제라고 단정하지 않는다. 다만 DB 비사용 경로도 혼합 과부하 때 느려지는 공통 경로 현상이 있고, 목록·주간 순위가 그 부하를 키운다는 점은 분리 시험으로 확인됐다.

## 판단과 다음 작업

1. **장르 화면의 주간 순위부터 5초 안팎의 짧은 캐시를 검토**하고, HOT과 같은 조건에서 결과 동일성과 화면 p95를 재검증한다. 현재 매 방문마다 판매량 집계와 순위 계산이 실행된다.
2. **이벤트 목록은 화면에 필요한 개수만 요청하도록 페이지 나누기 또는 제한을 적용**한다. 현재 장르 화면은 전체 목록을 읽어 일부를 ‘마감 임박’으로 정렬하고 전체를 ‘추천’에 그린다. 화면 요구 개수를 먼저 정해야 같은 결과를 보장할 수 있다.
3. 위 두 변경 뒤 동일한 8화면 k6 시나리오로 500·1,000방문/초와 1만 방문/10~20초를 다시 측정한다. 성공률 100%와 시작 수·미시작 수를 먼저 보고, 그다음 성공 방문의 p95와 서버 CPU·DB 시간을 평가한다. 부하 생성기를 별도 호스트에 두면 이번 PC Docker/NAT 경로의 변동도 분리할 수 있다.

- 시험 전과 최종 확인에서 로컬 원본은 **96 이벤트·163 티켓**, 별도 스키마는 **96/163, 500/859, 1,000/1,721**이었다. 로컬 DB 행은 삭제하지 않았다. 측정용 앱만 제거했고 로컬 DB는 종료 코드 0으로 정상 종료했다. 배포 DB는 이번에 넣은 측정용 행을 정리해 **0 이벤트·0 티켓·0 사용자·0 주문**으로 복원했다.
