마지막 테스트는 최대 목표까지 도달하기 전에 p95 5초 중단 기준을 넘겨 종료됐다. k6 실행 구간은 약 86.5초이며, 전체 HTTP 요청 3,313건에는 사전 확인 4건이 포함된다. 부하 구간 HTTP 요청 3,309건 중 28건이 실패했다. 939건의 dropped_iterations는 여유 가상 사용자가 부족해 시작하지 못한 요청으로, HTTP 실패율에 포함되지 않는다. 평균 HTTP 요청률 약 38.3/s는 증가 부하 전체 평균이며 최대 처리량으로 해석하면 안 된다.

저부하에서 0.5 CPU의 수치가 조금 더 낮은 것은 개선 효과가 아니다. 실행 순서, 캐시, 측정 변동이 섞이며 반복 횟수도 조건별 1회다.

## 별도로 확인한 심각한 병목

`GET /api/events?maxPrice=50000&availableOnly=true`는 부하를 넣기 전부터 실패했다. 2 CPU에서 3회, 0.5 CPU에서 3회 모두 약 8.36~8.43초 뒤 HTTP 403을 반환했다. DB 로그에는 `QueryTimeoutException`과 `maximum statement execution time exceeded`가 기록됐다. 이 테스트 환경에 설정한 SQL 제한은 8초이며, 원래 애플리케이션의 기본 제한이 아니다. 정상 응답시간이 8초라는 뜻이 아니라 그 시간까지 끝내지 못했다는 뜻이다.

이 API는 정상 응답을 검증할 수 없었으므로 위 혼합 부하 테스트에서 분리했다. 위 표의 낮은 오류율은 예매 가능 검색을 포함한 서비스 전체 오류율이 아니다.

실행 계획에서 주문 테이블 `o1_0`의 접근 방식은 `ALL`, 예상 스캔 행 수는 99,429였다. `orders.ticket_id` 인덱스가 없고 티켓별 예약 수량 합산에 주문 테이블 반복 스캔이 발생하는 구조다. 느린 쿼리 로그에서 각 실패 요청은 약 1,446만~3,223만 행을 읽었다. `results/available-explain.json`, `available-query.sql`, `available-slow-queries.tsv`, `order-indexes.tsv`에 근거가 있다.

고부하에서는 백엔드 CPU가 Docker 표시 기준 최대 53.54%로 0.5 CPU 제한 부근에 도달했다. 같은 측정에서 DB 최대 30.84%, k6 최대 12.86%였다. 백엔드 CPU 제한에 따른 병목과 일치하는 관찰이지만, 정확한 CPU 소비 함수는 프로파일링하지 않았다. 마지막 메모리는 백엔드 약 536.5MiB, DB 약 464.8MiB였다.

## 환경과 데이터

- Docker Desktop: 12 CPU, 약 15.4GiB 사용 가능. Windows 호스트에서 모든 구성요소를 실행.
- 애플리케이션·MySQL 각각 메모리 및 스왑 상한 768MiB. JVM 힙 256~384MiB.
- MySQL 8.0, InnoDB 버퍼 풀 128MiB. 쿼리 8초 제한, 느린 쿼리 기록 활성화.
- k6 v2.3.0, 별도 컨테이너 2 CPU / 1GiB 상한. 최대 가상 사용자 200.
- 합성 데이터: 사용자 1,000명, 행사 3,000개, 티켓 30,000개, 주문 100,000개.
- 주문은 20% PENDING, 80% EXPIRED. 실제 회원/주문 데이터를 복사하지 않음.
- 행사 날짜는 데이터 생성일 기준 미래로 설정. 공연·티켓 분포는 균일하므로 실제 인기 편중과 다름.
- 결제 복구·결제 대사·자동 가격 조정 스케줄러를 끔. SMTP·Gemini·결제 키를 주입하지 않음.
- 프로필마다 30초 워밍업 후 60초 동안 5 RPS 측정. 증가 부하는 각 30초씩 목표 25, 75, 150, 300 RPS.
- 읽기 API만 호출. HTTPS·Caddy·브라우저 렌더링·예매 생성·로그인·외부 API 성능은 제외.
- 기존 로컬 DB는 행사 96개, 티켓 315개, 주문 0개를 유지. 기존 설정과 소스 변경 없음.
- 전용 컨테이너는 측정 후 중지. 재측정용 이미지·DB 볼륨·결과 파일은 보관.

## 다음 개선 순서

1. 예매 가능 검색의 주문 조회 인덱스를 검토하고 실행 계획·응답시간을 같은 데이터에서 전후 비교한다. 인덱스만으로 충분한지 확인 후 집계 쿼리 구조를 검토한다.
2. DB 시간 초과가 HTTP 403으로 보이는 예외 처리 경로를 수정한다. 권한 오류와 서버 지연을 구분한다.
3. 전체 목록에 페이지네이션을 적용할 필요를 검토한다. 1회 약 1MB 응답이 고부하 직렬화·전송 비용을 높인다.
4. 같은 부하를 3회 이상 반복하고, 고정 요청률 구간을 추가해 목표 지연을 만족하는 지속 처리량을 찾는다.
