# 예매 대기열 설계 (초안)

상태: 구현 완료 (2026-11-17). 측정 결과는 [용량·대기열 보고서](../reports/2026-11-16-capacity-and-queue.md)에 있다.

## 왜 필요한가

2 vCPU 서버를 운영과 같은 구성(Caddy HTTPS → Spring Boot → MySQL)으로 측정한 결과([용량·대기열 보고서](../reports/2026-11-16-capacity-and-queue.md)):

| 인기 티켓 하나에 초당 주문 진입 | 주문 흐름 p95 | DB 커넥션 대기 |
|---|---|---|
| 25명 | 0.7~1.0초 | 6~8 |
| 50명 | 6~16초 | 63~189 |
| 150명 | 성공률 21~27% | - |

- 주문은 재고를 넘겨 팔지 않도록 **티켓 행을 잠그고(`FOR UPDATE`)** 처리한다. 한 티켓에 몰린 주문은 한 줄로 서서 처리되므로 CPU가 남아도 처리량이 늘지 않는다.
- 한계를 넘으면 요청이 DB 커넥션 대기열과 Caddy에 쌓여 응답이 수십 초로 늘고, 결국 시간 초과로 실패한다. 먼저 온 사람이 먼저 산다는 보장도 없다.

대기열은 **입장 속도를 서버가 감당하는 만큼으로 조절**하고, 기다리는 동안 **순번을 보여 주며, 먼저 온 순서대로** 들여보낸다. 재고 정합성은 지금처럼 DB 잠금이 지키고, 대기열은 부하와 공정성만 맡는다.

## 범위

- **대상:** `events.queue_enabled = true`인 공연(인기 공연의 예매 오픈). 관리자가 켜고 끈다. 일반 화면 조회에는 걸지 않는다.
- **막는 지점:** 주문 생성(`POST /api/orders`). 공연 상세 조회와 결제 화면은 그대로 둔다.
- **하지 않는 것:** 봇 차단, 좌석 지정, WebSocket 푸시, 서버 여러 대 운영(설계는 여러 대에서도 맞게 둔다).

## 흐름

```
[공연 상세] 예매하기
   │ queue_enabled = false → 지금처럼 바로 주문
   │ queue_enabled = true
   ▼
POST /api/queue/{eventId}            → Redis ZSET에 (userId, 도착 순서) 등록. 이미 있으면 순서 유지
   ▼
[대기 화면] GET /api/queue/{eventId} 를 안내받은 간격으로 반복
   │ { admitted: false, position: 1234, estimatedWaitSeconds: 62, nextPollSeconds: 30 }
   │ ...
   │ { admitted: true, expiresInSeconds: 300 }
   ▼
POST /api/orders                     → 입장권이 있어야 통과. 이후 기존 주문·결제 흐름 그대로
```

## Redis 자료 구조

| 키 | 타입 | 내용 |
|---|---|---|
| `queue:{eventId}:waiting` | ZSET | member = userId, score = 등록 순번(`INCR queue:{eventId}:seq`). 순번은 서버 시계와 무관하게 증가 |
| `queue:{eventId}:pass:{userId}` | STRING, TTL 300초 | 입장권. 있으면 5분 동안 주문 가능 |
| `queue:{eventId}:tick:{epochSecond}` | STRING, TTL 5초 | 그 1초의 입장 처리를 이미 한 서버가 있다는 표시 |
| `queue:active` | SET | 대기 인원이 있는 eventId 목록 |

- **등록:** `ZADD NX`라 새로고침하거나 다시 눌러도 맨 뒤로 밀리지 않는다. 이미 입장권이 있으면 바로 `admitted: true`.
- **순번:** `ZRANK`(O(log n)). DB를 보지 않는다. 대기열 순번을 먼저 보고, 없으면 입장권을 본다. 입장 처리가 대기열에서 빼는 일과 입장권을 만드는 일을 한 번에 하므로, 대기열에 없으면 입장권은 이미 있다. 반대 순서로 읽으면 두 읽기 사이에 입장 처리가 끼었을 때 사용자를 놓친다(측정 중 0.8% 발생 후 수정).
- **입장 처리(1초마다):** Lua 스크립트 하나로 원자적으로 실행한다.
  1. `SET tick:{초} NX EX 5`에 성공한 서버만 진행한다. 서버가 여러 대여도 1초에 N명만 들어간다.
  2. `ZPOPMIN waiting N` → 각 userId에 `SET pass:{userId} 1 EX 300`.
  3. 대기 인원이 0이면 `queue:active`에서 뺀다.
- **N(초당 입장 인원):** 설정 `queue.admit-per-second`, 기본 **20**. 측정에서 1초 안에 처리된 25명보다 여유를 둔 값이다.

## 주문 API의 입장권 검사

- `OrderService.createOrder`는 **트랜잭션의 첫 조회가 티켓 잠금이어야** 한다. 잠금 전에 일반 조회를 하면 REPEATABLE READ 읽기 시점이 먼저 고정돼, 마지막 1장에 100건이 팔리던 버그가 다시 생긴다.
- 그래서 입장권 검사는 **주문 트랜잭션 밖, 컨트롤러 앞단(`QueueGate`)**에서 한다.
  - 티켓 → 공연·`queue_enabled` 조회는 별도의 짧은 읽기 트랜잭션에서 한다.
  - 입장권은 Redis `EXISTS`로만 확인한다.
- 입장권이 없으면 **409 `QUEUE_REQUIRED`**로 돌려보내고, DB 잠금까지 가지 않는다. 대기열을 거치지 않은 요청이 잠금 경쟁에 끼지 않는다.
- 입장권은 주문 후에도 5분 동안 유지한다. 결제 화면 이탈 후 다시 주문하는 경우를 위해서다. 1인 점유 한도(티켓당 10장)는 기존 규칙이 그대로 막는다.

## 순번 확인 요청의 부하

측정상 이 서버는 일반 요청을 초당 약 440건 처리하고, HTTPS 처리에 CPU를 많이 쓴다. 대기 인원이 확인 요청으로 서버를 다 써 버리면 대기열이 오히려 병목이 된다.

- 확인 API는 **Redis만** 본다(`ZRANK`, `EXISTS`). DB와 JPA를 쓰지 않는다.
- 다음 확인 간격은 서버가 정한다: `nextPollSeconds = clamp(예상 대기 시간 / 2, 2, 30)`. 예상 대기 시간은 `순번 / N`초다. 앞쪽은 2초마다, 뒤쪽은 최대 30초마다 묻는다.
  - 측정에서 3,000명이 기다릴 때 확인 요청은 초당 약 100건이었다. 서버 한계(초당 약 440 요청)보다 충분히 작다.
- 브라우저는 HTTP/2 연결을 재사용하므로 확인 요청마다 TLS 비용이 들지 않는다.

## Redis 장애 시

**통과(fail-open)를 택한다.** 대기열 확인이 실패하면 주문을 그대로 진행시키고, 경고 로그와 지표를 남긴다.

- 이유: 재고 정합성은 DB 잠금이 지키므로, 대기열이 없어도 잘못 팔리지는 않는다. 느려질 뿐이다. 반대로 막으면(fail-closed) Redis 하나 때문에 예매 전체가 멈춘다.
- 기존 공연 목록 캐시도 Redis 장애 시 DB로 대체한다. 같은 원칙이다.

## 스케줄러

입장 처리는 1초마다 돌아야 하는데, 기존 스케줄러(결제 복구, 대사, 토큰 정리, 가격 조정)가 같은 스레드 풀(2개)을 쓴다. 복구 작업이 길어지면 입장이 밀리므로 **대기열 전용 스레드**로 분리한다.

## 화면

- 공연 상세: `queueEnabled`면 "예매하기"가 대기 화면(`/queue/:eventId`)으로 이동한다. 선택한 티켓과 수량을 함께 넘긴다.
- 대기 화면: "앞에 1,234명 · 예상 1분" 표시, 안내받은 간격으로 확인. 입장되면 넘겨받은 티켓과 수량으로 바로 주문하고 결제 화면으로 이동한다.

## 관측

- Grafana 패널 추가: 공연별 대기 인원(gauge), 초당 입장 수(counter), `QUEUE_REQUIRED` 거절 수, 대기열 Redis 오류 수.

## 검증

**테스트** (Redis가 필요한 테스트는 MySQL 테스트처럼 CI에 Redis 서비스 컨테이너를 붙여 실행)

| 확인할 것 | 방법 |
|---|---|
| 먼저 등록한 순서대로 입장 | 100명 동시 등록 후 입장 순서 = 등록 순서 |
| 다시 등록해도 순서 유지 | 같은 사용자 재등록 시 순번 변화 없음 |
| 1초에 N명만 입장 | 입장 처리 2개를 동시에 돌려도 N명 |
| 입장권 없으면 주문 거절, DB 잠금 안 함 | 409 `QUEUE_REQUIRED`, 티켓 잠금 쿼리 미실행 |
| 입장권 만료 | TTL 이후 주문 거절 |
| 대기열 꺼진 공연은 영향 없음 | 기존 주문 테스트 전부 통과 |
| Redis 장애 시 통과 | Redis 중단 상태에서 주문 성공 |
| 마지막 1장 동시 주문 회귀 | 기존 `LastTicketConcurrencyTest` 통과 |

**부하 측정** (같은 2 vCPU 환경, Caddy 경유)

- 시나리오 "예매 오픈": 10초 동안 3,000명이 한 공연에 몰림.
- 대기열 없음 vs 있음 비교: 주문 성공률, 주문 p95, DB 커넥션 대기, CPU, 확인 요청 수, 마지막 사람의 대기 시간.
- 기대: 대기열이 있으면 주문 단계 p95가 1초 안쪽으로 유지되고 시간 초과가 없어야 한다. 대신 사용자는 순번만큼 기다린다(3,000명 / 초당 20명 = 약 150초).
- 결과: 30초에 3,000명이면 주문 p95 10.9초 → 0.69초, 3,001명 모두 주문. 10초에 3,000명이면 공연 화면 조회와 대기열 등록만으로 서버 한계를 넘어 주문 p95가 8~10초였다(성공률은 99.7% 이상). 자세한 내용은 보고서에 있다.

## 다음 과제 (이번 범위 밖)

- 주문할 때마다 그 티켓의 결제 대기 수량을 다시 합산하는 구조라, 대기 주문이 쌓일수록 주문 한 건이 느려진다. 티켓에 점유 수량을 따로 두면 잠금 시간을 줄일 수 있지만, 만료·취소·결제 복구 경로를 모두 바꿔야 해서 별도로 진행한다.
- 일반 화면 과부하(초당 100명 근처에서 스레드 포화)는 대기열로 해결되지 않는다. 과부하 시 빨리 거절하는 설정(Caddy 동시 연결 상한 등)은 따로 측정한다.
