# CDN과 엣지 대기실 설계 (초안)

상태: 구현 완료, 배포·측정 전 (2026-11-17). [서버 내 대기열](waiting-queue.md)의 다음 단계다. 배포 방법은 [배포 문서](../deploy.md#cdn과-엣지-대기실-cloudfront)에 있다.

## 왜 필요한가

[측정](../reports/2026-11-16-capacity-and-queue.md)에서 서버 안의 Redis 대기열은 1만 명이 100초에 걸쳐 올 때는 전원을 주문까지 보냈지만, 20초에 몰리면 19%만 성공했다. 대기열 앞 단계에서 서버가 넘쳤다.

- 새 방문자마다 맺는 HTTPS 연결(Caddy)이 CPU 1개 가까이를 썼다.
- 공연 상세 조회가 매번 DB까지 갔다.
- 대기열 등록과 순번 확인도 결국 같은 서버의 CPU를 썼다.

2 vCPU 서버 하나가 받아들일 수 있는 새 방문자는 초당 약 100명이다. 20초에 1만 명은 그 5배다. 이 일들을 서버 밖으로 옮긴다.

## 구조

```
브라우저 ──HTTPS──▶ CloudFront (서울 엣지)
                    ├─ /assets/*            정적 파일, 1년 캐시 (파일명에 해시)
                    ├─ /api/events*  (GET)  공연 목록·상세, 2초 캐시 (공개 데이터, 쿠키·인증 헤더 무시)
                    ├─ /api/queue/*         ─▶ API Gateway ─▶ Lambda ─▶ DynamoDB   (엣지 대기실)
                    └─ 그 밖 (/api/*, 화면)   캐시 없음, 쿠키·인증 헤더 전달 ─▶ Lightsail (Caddy ─▶ Spring)
```

- 브라우저와의 HTTPS는 CloudFront가 맺는다. 서버에는 CloudFront가 재사용하는 소수의 연결만 들어온다.
- 공연 상세는 엣지에서 2초 동안 같은 응답을 돌려준다. 1만 명이 와도 서버에는 2초에 한 번 정도만 간다.
- 대기열 등록과 순번 확인은 Lambda가 처리해 **서버에 오지 않는다.** 경로와 응답 형식을 서버 내 대기열(`/api/queue/{eventId}`)과 같게 맞춰, 프론트 대기 화면은 그대로 쓴다.
- 서버는 입장한 사람(초당 20명)의 주문·결제만 처리한다.

## 엣지 대기실

### 데이터 (DynamoDB, 온디맨드)

| 항목 | 키 | 값 |
|---|---|---|
| 공연별 상태 | `event#{eventId}` | `issued`(지금까지 받은 번호), `admitted`(입장시킨 번호), `waiting`(대기 중 여부) |
| 사용자 번호 | `ticket#{eventId}#{userId}` | 내 번호. 다시 들어와도 같은 번호 |

### 동작

- **등록:** 사용자 번호가 없으면 `issued`를 원자적으로 1 올려(`ADD`) 내 번호로 저장한다. 조건부 쓰기로 같은 사용자가 두 번 받지 않게 한다. 새로고침해도 번호가 유지된다.
- **입장:** 입장 Lambda가 1분마다 실행되어 그 1분 동안 1초마다 공연별로 `admitted = min(issued, admitted + 20)`을 갱신한다. `issued`를 넘지 않으므로, 한동안 아무도 없다가 사람이 몰려도 한꺼번에 들여보내지 않는다. 실행이 경계에서 겹쳐도 공연 항목에 마지막으로 처리한 초(`sec`)를 조건부로 기록해, 같은 초에 두 번 입장시키지 않는다.
- **입장권 만료:** 처음 입장 토큰을 준 시각(`at`)을 기록하고 5분 뒤 만료한다. 순번 확인을 반복해도 늘어나지 않는다. 만료 뒤 다시 등록하면 새 번호로 맨 뒤에 선다.
- **순번 확인:** 내 번호와 `admitted`를 비교한다. 내 번호가 `admitted` 이하면 **입장 토큰**을 준다. 아니면 순번(내 번호 − admitted), 예상 대기 시간, 다음 확인 간격(앞쪽 2초 ~ 뒤쪽 30초)을 준다. 서버 내 대기열과 같은 규칙이다.
- **사용자 확인:** 요청의 Authorization 헤더(서비스의 액세스 토큰)를 Lambda가 같은 키로 검증해 사용자 ID를 얻는다. 로그인하지 않으면 401이다.

### 입장 토큰

- JWT(HS256), 내용은 사용자 ID, 공연 ID, 만료(5분). 서명 키는 Lambda와 서버만 안다.
- 프론트는 주문 요청에 `X-Queue-Token` 헤더로 붙인다.
- 서버의 `QueueGate`는 토큰 서명·사용자·공연·만료를 검사한다. DB와 Redis를 보지 않으므로 서버 내 대기열보다 가볍다. 토큰이 없으면 지금처럼 Redis 입장권을 본다(서버 내 대기열, 로컬 개발용).

## 캐시하면 안 되는 것

- 로그인, 토큰 재발급, 주문, 결제, 마이페이지, 관리자 API는 **캐시하지 않고** 쿠키와 Authorization 헤더를 그대로 전달한다.
- 캐시하는 공연 API는 캐시 키에 쿠키와 인증 헤더를 넣지 않고, 서버에도 전달하지 않는다. 사용자마다 다른 내용이 섞일 수 없다. 서버는 이 API들에만 `Cache-Control: public, max-age=2`를 붙인다.
- `index.html`은 캐시하지 않는다. 배포 직후 새 화면이 바로 보이게 하기 위해서다.

## 바뀌는 것

| 대상 | 내용 |
|---|---|
| 접속 주소 | `https://xxxx.cloudfront.net` (Lightsail 주소는 서버 원본으로 계속 씀) |
| 토스 결제 | 성공·실패 주소를 현재 주소(`window.location.origin`)로 만들므로 변경 없음 |
| 네이버 지도 | 콘솔에 새 주소 등록 필요 |
| README·노션·UptimeRobot | 새 주소로 변경. `/health`와 `/grafana`는 원본 주소도 유지 |

## 비용

이 프로젝트 규모에서는 무료 사용량 안이다. CloudFront 월 1TB·1천만 요청, Lambda 월 100만 요청, DynamoDB 온디맨드는 1만 명 측정에 수 센트 수준이다. 입장 Lambda는 1분마다 60초씩 돌아 한 달 약 5,400 GB-초를 쓰며, 무료 사용량(40만 GB-초) 안이다.

## 인프라 관리

- `infra/edge/`에 CloudFormation 템플릿과 Lambda 코드(Python)를 둔다. 콘솔에서 템플릿을 올려 스택을 만든다.
- 비밀 값(서비스 JWT 키, 입장 토큰 키)은 스택 파라미터(`NoEcho`)로 받는다.
- Lambda 코드는 pytest와 moto(가짜 DynamoDB)로 테스트하고 CI에서 돌린다.

## 검증

| 확인할 것 | 방법 |
|---|---|
| 번호 순서, 재등록 시 번호 유지, 동시 등록에 중복 번호 없음 | Lambda 단위 테스트 |
| 입장은 초당 N명, issued를 넘지 않음, 쉬다가 몰려도 한 번에 안 들어감 | Lambda 단위 테스트 |
| 위조·만료·다른 사용자·다른 공연 토큰 거절 | 서버 테스트 |
| 토큰 없이 주문하면 티켓 잠금 전에 409 | 서버 테스트 |
| 캐시 응답에 개인 정보 없음 | 로그인 상태로 공연 API 응답 비교 |
| 20초 1만 명 | CloudFront 경유로 다시 측정. 서버 CPU, 성공률, 주문 p95 비교 |
